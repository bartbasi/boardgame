**Proposed decisions**

1. Database collation: initialize PostgreSQL with `POSTGRES_INITDB_ARGS="--locale-provider=builtin --locale=C.UTF-8"` (in deploy/docker-compose.yml now; must be in place before T-071's first database start). Sources, all checked 2026-10-13:
   - https://www.postgresql.org/docs/18/locale.html (23.1.4 Locale Providers): "The builtin provider uses built-in operations. Only the C, C.UTF-8, and PG_UNICODE_FAST locales are supported"; for C.UTF-8 "the behavior is based on Unicode. The collation uses the code point values only", with POSIX-compatible character classes and simple case mapping. libc: "The same locale name may have different behavior on different platforms". 23.1.1: LC_COLLATE and LC_CTYPE "affect the sort order of indexes, so they must be kept fixed, or indexes on text columns would become corrupt".
   - https://www.postgresql.org/docs/18/collation.html (23.2.2.1, `pg_c_utf8`): "Behavior is efficient and stable within a PostgreSQL major version."
   - https://www.postgresql.org/docs/18/sql-altercollation.html (Notes): collation changes "can lead to corrupt indexes", for example "when upgrading the operating system to a new major version"; libc versions are recorded only on glibc, FreeBSD, and Windows.
   - https://www.postgresql.org/docs/18/app-initdb.html: default provider is libc; with `--locale-provider=builtin`, `--locale` or `--builtin-locale` "must be specified and set to C, C.UTF-8 or PG_UNICODE_FAST".
   - https://hub.docker.com/_/postgres: `POSTGRES_INITDB_ARGS` passes arguments to initdb; the image's default locale is `en_US.utf8`.
   - Measured in the pinned image: the default gives provider libc, `en_US.utf8`, and an empty `datcollversion` (musl records no collation version, so PostgreSQL could never warn about a change); with the proposed arguments: provider `b`, `datlocale` C.UTF-8, `datctype` C.UTF-8, encoding UTF8, `datcollversion` 1. Sorting `b B a A é e Z _x` gives `A B Z _x a b e é` in both (musl's libc sort is code point order too), so nothing visible changes today; what changes is that the order is defined by PostgreSQL and cannot move under an Alpine or Debian base image change or the amd64 to arm64 move. `upper('ß')` stays `ß` (simple case mapping) where libc gives `ẞ`. The image prints "no usable system locales were found" with or without the option (musl).
   - Why not PG_UNICODE_FAST (also builtin, full case mapping): it exists only from PostgreSQL 18, and no feature needs full case mapping; titles are matched by BGG, and the app sorts its own lists. Why not ICU: its results "may depend on the version of the ICU library", the problem we want to avoid. Why `--locale` and not only `--builtin-locale`: it also sets LC_CTYPE to C.UTF-8 instead of musl's nominal `en_US.utf8`.
2. Migrations as Dart constants in lib/src/db/migrations.dart, append only, SHA-256 checksum per migration, advisory lock, one transaction per migration; exit codes 69 (database unreachable at startup) and 70 (migration failed or history mismatch).
3. Startup waits up to 30 s for PostgreSQL [ASSUMPTION]; pool connect timeout 5 s and query timeout 10 s [ASSUMPTION]; `DATABASE_POOL_MAX` at most 20.
4. /health body adds `database` (`ok` or `unavailable`); on 503 `status` is `unavailable`. The /health database check: one probe at a time, 1 s cache, 1 s limit.
5. Tests that start the server need a real PostgreSQL (`TEST_DATABASE_*`); route tests that do not involve the database use `DatabaseHealth.alwaysUp()`.
6. `describeError` logs PostgreSQL server errors as severity and SQLSTATE only.

**Must fix**

- **R1-M1 (T-019-B1, QA): a migration can end its own transaction, so AC3's rollback does not hold, and the suite is red.** server/lib/src/db/migration.dart:114-134 (`validateMigrations`) and :230-235 (`tx.execute(m.sql, queryMode: QueryMode.simple)`). I agree with QA's analysis: in the simple query protocol a `COMMIT` inside the string commits the transaction `runTx` opened, and the remaining statements run outside it. Reproduced: `sh server/tool/test_linux.sh` gives 330 run, 1 skipped, 1 failed (QA's atomicity test). Why must fix rather than "accepted": the failing test blocks the ticket either way, the fix is small, and the failure mode in production is bad (the next start re-runs the half-applied migration and fails forever, so the server never comes up after a deploy). Only our own reviewed migrations can trigger it, which is why I would not call it a security issue.
  Suggested fix: make `validateMigrations` reject transaction control, and add the rule to the `Migration` doc comment. Cover every spelling PostgreSQL accepts, case-insensitive: `BEGIN`, `START TRANSACTION`, `COMMIT` (also `COMMIT AND CHAIN`, `COMMIT PREPARED`), `END`, `ROLLBACK` (also `ROLLBACK TO`, `ROLLBACK PREPARED`), `ABORT`, `SAVEPOINT`, `RELEASE`, `PREPARE TRANSACTION`. Match only at the start of a statement (start of the SQL or after `;`), after removing `--` and `/* */` comments, and skip single-quoted and dollar-quoted text; otherwise the `END;` and nested `BEGIN` inside a `$$ ... $$` PL/pgSQL body (likely in a later trigger function) would be refused. A false positive only fails at startup in tests, so a simple scanner is fine; a missed spelling is the real risk, so test each keyword, lower case, and leading whitespace/comments. Note for QA: the rejection throws `MigrationStateException`, so QA's test at server/test/qa/database_edge_cases_test.dart:276-285 should expect `isA<MigrationException>()` (the sealed base) while keeping its "sneaky does not exist" check; that is QA's file, so the orchestrator should route it. Optional defense in depth: read `pg_current_xact_id()` at the start of the transaction and again after `m.sql`, and fail with a clear message if they differ.

**Should fix**

- **R1-S1: the AC5 pool test samples once after a fixed 150 ms, so it is timing-flaky and proves the cap at one instant only.** server/test/db/startup_test.dart:183-195. QA saw it fail under load. A flaky test will eventually turn a CI run red for no reason. Fix: while the five `pg_sleep` queries run, poll `pg_stat_activity` every ~20 ms until all of them complete, record the maximum count, and assert the maximum is exactly 2 (proves both "reaches the cap" and "never exceeds it"); raise the sleep to about 0.5 s so connection setup on Windows cannot hide the overlap.

**What changed, per finding**

- **R1-M1 (QA T-019-B1), fixed.** New `server/lib/src/db/transaction_control.dart`: `findTransactionControl(sql)` is a small lexer that returns the transaction control statement it finds, or null. It looks only at the first word (or first two) of each statement: the start of the SQL and after each `;`. It skips whitespace, `--` comments, nested `/* */` comments, single-quoted strings (including `E'...'` with backslash escapes and `''` doubling), double-quoted identifiers, and dollar-quoted text (`$$`, `$tag$`; a `$` after an identifier character, or `$1`, is not a quote). Inside a SQL-standard body (`BEGIN ATOMIC ... END`, with `CASE ... END` nesting) a `;` does not start a statement. Refused, case-insensitive: `BEGIN`, `COMMIT` (so also `COMMIT AND CHAIN`, `COMMIT PREPARED`), `END`, `ROLLBACK` (also `ROLLBACK TO`, `ROLLBACK PREPARED`), `ABORT`, `SAVEPOINT`, `RELEASE`, `START TRANSACTION`, and `PREPARE TRANSACTION` (`PREPARE name AS ...` stays allowed). `validateMigrations` calls it and throws `MigrationStateException("migration N (name) contains a COMMIT statement; every migration already runs in its own transaction, so remove it")`; startup logs `migrations cannot run` and exits 70 before touching the database. A false positive can only fail startup in tests (the safe direction). `CALL` and `DO` need no rule: inside our transaction PostgreSQL refuses a COMMIT in them ("invalid transaction termination"). **Scanner review: can transaction control get through, and is valid SQL refused?**

I read the scanner against PostgreSQL's lexer rules and ran a scratch probe of `findTransactionControl` (pure Dart, outside the repo). It holds for every spelling in the Migration doc, for case, comments (nested `/* */`, `--` ended by LF or CR), all six whitespace bytes, single-quoted, E'', double-quoted, and dollar-quoted text with any tag, and for `$1` parameters. These match PostgreSQL:
- dollar-quote closing as first occurrence of the exact tag;
- `$` as an identifier character;
- E'' detection only at a token start;
- `/*` and `--` starting a comment even inside an operator.

Unterminated quotes or comments stop the scan. That is safe: the simple query protocol parses the whole string before running any statement, so a lexing or syntax error means nothing runs. A transaction control statement inside a DO block or a CALLed procedure fails in PostgreSQL itself ("invalid transaction termination"), because `runTx` has already opened a transaction block.

No false refusals found:
- PL/pgSQL in `$$` and `$fn$` bodies, `DO $$ BEGIN ... END $$`, old-style single-quoted function bodies, `PREPARE name AS ...`, and `BEGIN ATOMIC ... END` with nested `CASE ... END` all pass.
- `CREATE RULE ... DO (a; b)` only splits on `;`. The pieces it produces cannot validly start with a refused word.
- Over-refusals the developer accepts (for example Dart's `toUpperCase` turning dotless `ı` into `I`) fail in the safe direction.

Findings:

- **R3-S1 (should fix, follow-up ticket): `BEGIN ATOMIC` mode starts on any `begin` word followed by `atomic`, not only in a function body, so a later COMMIT is hidden.** server/lib/src/db/transaction_control.dart:120-121. Probe: `SELECT begin atomic FROM (SELECT 1 AS begin) s; COMMIT; SELECT 1;` returns null (not refused). BEGIN and ATOMIC are unreserved keywords, so `begin` is a valid column name and `atomic` a valid bare column label (PostgreSQL 14 and later), and the statement is valid. After it, `atomicDepth` stays 1, `;` no longer starts a statement, and the COMMIT reaches PostgreSQL, which is T-019-B1 again. Nobody writes this by accident, and migrations are our own reviewed code, so it does not block. But the scanner exists to make this impossible, and the fix is small:
  - only enter atomic mode when the statement's first word is CREATE and FUNCTION or PROCEDURE has been seen in it;
  - also refuse when the scan ends with `atomicDepth > 0`. PostgreSQL would reject an unterminated body anyway, so this costs nothing and catches other miscounts.
  - Add the probe string as a test.
- **R3-G1: a migration can turn `standard_conforming_strings` off for the rest of the session.** With it off, PostgreSQL treats a backslash in a plain `'...'` string as an escape and the scanner does not. Probe: `SELECT 'a\'; SELECT '; COMMIT; SELECT 'x';` is one string followed by `COMMIT` for PostgreSQL, but the scanner returns null. The setting is on by default and nothing sets it. A plain `SET` in migration N would last for migration N+1 on the same pooled connection, though. Cheap guards: `migrate` runs `SET standard_conforming_strings = on` on its connection before each migration, or the scanner refuses the setting's name.
- **R3-G2: `$` right after a digit.** The scanner does not start a dollar quote after a digit (transaction_control.dart:97, digits count as identifier characters). PostgreSQL's lexer ends the number and does start one (`1$$...$$`). Probe: `SELECT 1$$ $$; COMMIT; SELECT $$x$$;` returns null. I found no grammar position where a number is directly followed by a string constant, so PostgreSQL rejects every such string with a syntax error and nothing runs. Not exploitable as far as I can see. Worth a comment, or treat a digit run that started a token as a number.

## Proposed decisions

For the orchestrator to record in docs/decisions.md:

1. **TLS between server and PostgreSQL:** off while both run on one VM on the internal Compose network, with scram-sha-256 authentication. If PostgreSQL ever moves off the host, TLS with `verify-full` must come with the move, because the driver answers a cleartext password request (review R1, open question 2). Reason: no network hop to protect today; the move is the trigger.
2. **"Unhealthy" in Compose is a status only.** While PostgreSQL is down the server container shows unhealthy, and nothing restarts containers for that (no autoheal tool, no script). Reason: a restart would turn a database blip into a loop of exit 69 starts. T-071 AC1 enforces it.
3. **Migrations may not contain transaction control statements** (BEGIN, START TRANSACTION, COMMIT, END, ROLLBACK, ABORT, SAVEPOINT, RELEASE, PREPARE TRANSACTION). Startup refuses them with exit 70 before touching the database. Reason: each migration already runs in its own transaction, and an embedded COMMIT breaks rollback (QA T-019-B1).
4. **Fail fast at startup on SQLSTATE 28P01, 28000, and 3D000** (wrong password, authorization refused, no such database): exit 69 after the first attempt. Socket errors and 57P03 are still retried for the startup timeout (30 s [ASSUMPTION]). Reason: an operator learns of a typo at once instead of after 30 s.
5. **PostgreSQL errors in logs:** a server error is logged as severity and SQLSTATE only, and any other `PgException` from the driver as its type and severity only, never the message. Only the `migration failed` line adds PostgreSQL's message, because that SQL is ours. Reason: messages can quote query values such as barcodes or search text (T-008 privacy rule).
6. **/health stays server-only** and is not part of packages/api_contract. It returns `status`, `version`, and `database` (`ok` or `unavailable`; 503 with `status: "unavailable"` when the database is down). Reason: it is an operations endpoint for Docker's health check and the operator; the app never calls it. (Already decided by the orchestrator in round 2; this records it.)
7. **Database collation:** initialize PostgreSQL with `POSTGRES_INITDB_ARGS="--locale-provider=builtin --locale=C.UTF-8"` (deploy/docker-compose.yml and server.yml now), in place before T-071's first database start, because it only takes effect on an empty data directory. Reason (developer round 1, proposed decision 1, official PostgreSQL 18 docs checked 2026-10-13): the builtin C.UTF-8 order is code point order defined by PostgreSQL and "stable within a PostgreSQL major version", so it cannot shift under an Alpine or Debian base image change or the amd64 to arm64 move; musl's libc locale records no collation version, so PostgreSQL could never warn about a change. Not PG_UNICODE_FAST (only from PostgreSQL 18, no feature needs full case mapping) and not ICU (results depend on the ICU library version). Visible effect today: none (the sort order matched in the measurement); `upper('ß')` stays `ß`. This answers the 2026-10-12 entry that left the collation to T-019. Once recorded, deploy/README.md and deploy/docker-compose.yml should point to docs/decisions.md instead of this handoff (review R1-G4).
