**Behaviour**

- **Lookup:** a stored confirmed match answers first, with no request. If the match store cannot be read, the lookup falls through to the backend. The backend answer is stored only when `isStorableMatch` is true (status `matched`, gtin13 equals the looked-up key, exactly one game). An answer for another code is refused with `UnexpectedFailure` and nothing is stored. The data source already refuses it (T-028 D2); this is a second check. If saving the match fails, the match is still returned and the error is logged. Backend failures are returned unchanged.
- **confirmMatch:** a bggId below 1 gives `InvalidInputFailure(invalidBggId)` and nothing is written. Otherwise it saves or replaces the match. A store failure gives `StorageFailure`.
- **getGame:**
  - A remote success is cached with fetchedAt and lastViewedAt both set to `clock.now()` (UTC), and returned as fresh. A cache write failure still returns fresh data.
  - When the load fails and `servesCachedCopy` is true, the cached copy is returned as stale with its stored fetchedAt, and the view is recorded. Those failures are no connection, timeout, service unavailable, and rate limited.
  - The load failure is returned instead when there is no copy, the copy cannot be read or decoded, or the copy is for another bggId.
  - Every other failure (not found, invalid input, access denied, cancelled, configuration, unexpected) is returned as is, even when a copy is cached.
  - Details for another bggId give `UnexpectedFailure` and are not cached.
- **searchGames:** passes straight to the remote. No store calls.
- Swallowed problems are logged in debug builds only. The log line holds the operation and the failure or error type, never stored data.

### Proposed decisions

1. Rate limited (429) also serves the cached copy as stale. AC5 lists only no connection, timeout, and service unavailable, but 429 is just as transient, and showing cached data beats an error. To drop it, remove one line in `servesCachedCopy` and move one test row.
2. The cached details are the api_contract `GameDetailResponse` JSON. A cached copy that no longer decodes, for example after a contract change, counts as "no cached copy" and is never an error.
3. `GameDetailsSnapshot.fetchedAt` is when this device received the details. `GameDetails.fetchedAt` stays the backend's BGG fetch time. The store's fetchedAt (also used for eviction) is the device time.
4. The repository checks the code and the bggId again after the data source (defense in depth for T-028 D2). A mismatch is `UnexpectedFailure` and nothing is stored.
5. Device storage errors never fail a call the backend answered. They are logged by type, and only the offline copy or the remembered match is lost.

## Open questions

- For T-034 or UX: which time should "Details last updated N ago" show, the device fetch time (`GameDetailsSnapshot.fetchedAt`) or the backend's BGG fetch time (`GameDetails.fetchedAt`)? If the backend serves BGG data cached for days, "just now" from the device time could mislead. Both are available, so the screen can choose without a repository change.
