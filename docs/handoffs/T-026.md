### Developer notes (flutter-developer)

**What changed**

- `app/lib/features/scanner/domain/barcode.dart` (new): `Barcode.parse(String)` returns `Result<Barcode>`. It trims surrounding whitespace, then checks in this order: only ASCII digits, length 8, 12, or 13, then the GS1 check digit. A `Barcode` has `digits` (trimmed input), `format` (`ean8`, `upcA`, `ean13`, from the digit count), and `gtin13` (digits left-padded with zeros to 13). Equality and hashCode use `gtin13` only, so `036000291452` and `0036000291452` are the same value. No Flutter, plugin, or api_contract imports; it imports only `core/domain/result.dart`.
- `app/lib/core/domain/failure.dart`: new sealed case `InvalidBarcodeFailure(reason, length:)` and enum `InvalidBarcodeReason { nonDigit, wrongLength, badCheckDigit }`. It had to live here because `Failure` is sealed (subclasses must be in its library). It is separate from `InvalidInputFailure(InvalidInputCode.invalidBarcode)`, which stays the server's 400 answer; the new one means "rejected on the device, nothing sent".
- `app/lib/core/data/network/failure_mapper.dart`: `isRetryable` lists the new case as not retryable (the switch is exhaustive).
- `app/test/coverage_imports_test.dart`: regenerated with `dart run tool/coverage_check.dart --write-imports`.

- Empty input: the ticket lists only three reasons, so an empty or whitespace-only input is `wrongLength` with `length: 0`. copy.md has a separate `manualEntry.errorEmpty`; the manual entry screen (T-031) should show `errorEmpty` when `length == 0` and `errorLength` with `{count}` = `length` otherwise. If PM or UX prefer a separate `empty` reason, it is a one-line enum change.
- Order of checks: non-digit first, then length, then check digit, so `12A` is "non-digit" rather than "wrong length". This matches the manual-entry spec, where non-digits are the fallback error.

- 14-digit GTIN-14 is rejected (AC2, manual-entry spec section 9).
- Only ASCII digits count; other Unicode digits are `nonDigit`.

### Review (code-reviewer): APPROVED

Review, round 1. Verdict: APPROVED (0 must fix, 1 should fix, 4 suggestions; 1 item pending PM).

Scope: `git diff main...HEAD` (7 commits). Ownership: developer commits touch app/ and docs/handoffs only; QA commits touch app/test/qa, the handoff, and QA memory only. Main is 2 docs-only commits ahead; T-026 acceptance criteria are unchanged there and a trial merge (`git merge-tree`) is clean.

What I checked and found correct:
- Validation order: trim, then ASCII digits only (`^[0-9]*$`, so empty passes to the length check), then length 8/12/13, then check digit. Matches the ticket, the manual-entry spec (non-digit is the fallback error; empty is `wrongLength` with length 0, which T-031 maps to `manualEntry.errorEmpty`) and copy.md (`errorLength` `{count}` is the digit count, which `length` holds for `wrongLength`).
- Check digit: on the zero-padded 13-digit string, index i of the first 12 gets weight 3 when i is odd, so the digit next to the check digit (i = 11) has weight 3, as GS1 requires; leading zeros add nothing, so one routine is correct for EAN-8, UPC-A, and EAN-13. Verified by hand for `96385074` (sum 86, check 4) and `036000291452`. The test "exactly one check digit is accepted for each length" and the known real codes give an oracle independent of the implementation.
- Non-ASCII digits (Arabic-Indic, full-width) are `nonDigit`. That is the right call: the server contract (`invalid_barcode`: UPC-A, EAN-13, EAN-8) is ASCII, and the manual-entry field drops non-digits before validation, so this is only the fallback path.
- Canonical key: `padLeft(13, '0')` for every format; equality and hashCode use `gtin13` only, consistently. UPC-A gets one zero (AC4, satisfied). EAN-8 gets five zeros: PENDING PM confirmation of the GS1 rule (Open question 1), not a finding. The code is internally consistent with it: `96385074`, `0000096385074`, and the 12-digit `000096385074` all share one key, which is what the GS1 padding rule implies.
- `InvalidBarcodeFailure` in core/domain/failure.dart: required, since `Failure` is sealed. The only exhaustive `switch` on `Failure` in lib is `isRetryable` (updated, not retryable); there are no wildcard switches over `Failure` in lib that would silently swallow the new case. The test-side exhaustive switch in failure_test.dart was updated too. Keeping it separate from `InvalidInputFailure(InvalidInputCode.invalidBarcode)` (server 400) is clear and documented.
- Domain purity: barcode.dart imports only core/domain/result.dart (which re-exports failure.dart); architecture test passes. No `coverage:ignore` markers. barcode.dart 29/29 lines.
- Tests: AC1 to AC5 each have named tests, AC2 is table-driven with the exact failure value (reason and length) asserted, not just `isErr`.
- No em dashes or double-hyphen dashes in the diff.

Findings:

- R1-S1 (should fix) app/lib/core/domain/failure.dart:116-118. The doc on `length` says "How many characters the input had after trimming", but it is `String.length`, which counts UTF-16 code units: QA's emoji case `'0360002914😀'` gives 12, not 11 characters. Harmless today because only `wrongLength` uses it (all ASCII digits, so units equal characters), but a later caller could show it for `nonDigit`. Fix: say "UTF-16 code units of the trimmed input; meaningful as a digit count only for `wrongLength`", or set length only for `wrongLength`. One-line doc change.
- R1-G1 (suggestion) app/lib/features/scanner/domain/barcode.dart:3-5. The library doc says the rules "match the server's barcode validation in T-025", but T-025 is not built yet. Word it as a requirement ("T-025 must use the same rules") so a reader does not take it as verified, and note it in the T-025 handoff so the server reviewer checks it.
- R1-G2 (suggestion) barcode.dart:66-70. Two equal barcodes can differ in `digits` and `format` (`036000291452` upcA vs `0036000291452` ean13). This is what AC4 asks for and the class doc says so, but a Set or Map keeps whichever came first, so any UI that shows "the code you scanned" should read `digits` from the instance it parsed, not from a deduplicated collection. Worth a sentence in the class doc for T-030/T-031.
- R1-G3 (suggestion) All-zero codes (`00000000`, `000000000000`, `0000000000000`) pass and become a lookup. GS1 never issues them; a misread could send a pointless GameUPC call. Not in the ticket, and any rule here must match T-025, so leave it unless PM wants it (would be a new reason, or `badCheckDigit`).
- R1-G4 (suggestion) app/test/qa/barcode_edge_cases_test.dart:12-20. `withCheck` re-implements the production algorithm, so the off-by-one and length-sweep tests share its assumptions. They are fine as robustness tests because the developer's known-code tests are the independent oracle; if QA extends this file, prefer published codes.

Forward items (not findings on this ticket):
- T-030 scanner: filter by symbology before `Barcode.parse`. A UPC-E code is 8 digits and passes the EAN-8 check digit roughly one time in ten, which would produce a wrong key. backlog T-030 AC4 already requires ignoring UPC-E; make sure the test sends an 8-digit UPC-E raw value whose check digit is EAN-8 valid.

The server in T-025 must use the same rule so the local and server match stores agree. backend-developer and PM, please confirm, or add the fact to api-research.md.

## Proposed decisions

1. Barcode GTIN-13 key: every accepted code is left-padded with zeros to 13 digits (UPC-A gets one zero, EAN-8 gets five, EAN-13 unchanged). The app (T-026) and the server (T-025) use the same rule.
2. On-device barcode validation returns `InvalidBarcodeFailure(reason, length)` from core/domain; the server's 400 `invalid_barcode` stays `InvalidInputFailure(InvalidInputCode.invalidBarcode)`. An empty input is `wrongLength` with length 0, shown with `manualEntry.errorEmpty`.
