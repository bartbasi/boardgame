#### Proposed decisions

1. `lib/app/` is the composition root (root widget, router, shell). It imports feature screens, so it cannot live in `lib/core/`, which features import. Shared code stays in `lib/core/`.
2. The title search screen lives in `lib/features/scanner/presentation/` with the rest of the lookup flow (scan, manual entry, title search, lookup result). T-032 lists `app/lib/features/*/presentation/` without naming the feature.
3. Navigation uses go_router (BSD-3-Clause) with `StatefulShellRoute.indexedStack`, one navigator per destination.
4. Generated files (Riverpod `*.g.dart`, gen-l10n output) are committed, and CI checks they are up to date.
5. Domain code may import only non-UI `dart:` libraries, its own package (not a feature's data or presentation layer), and an allowlist of pure Dart packages: collection, equatable, freezed_annotation, json_annotation, meta. The architecture test enforces this, following own-package imports transitively. Adding a package to the allowlist is a reviewed change to `test/architecture/domain_purity.dart`.

They exist only until the real screens replace the placeholders (T-032, T-039, and the scanner and settings tickets), and the strings test skips keys that start with `dev`. OK to keep them out of copy.md?
2. (Orchestrator) AC11 needs an emulator. Install the Android `emulator` package and system images for API 24 and API 36 (x86_64), or approve testing on a physical device. I did not download them.
3. (UX) The NavigationBar reads both the semantic label and the visible label ("Scan a barcode, Scan, Tab 1 of 4"), because Flutter's NavigationBar takes its label as plain text. The rail reads only the semantic label. Is the bar's reading acceptable, or should the bar use only the visible label?
