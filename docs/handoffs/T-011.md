**What changed**

- `.github/workflows/server.yml` (new). Two jobs, run in parallel:
  - `dart` (matrix: `server`, `packages/api_contract`): `dart pub get --enforce-lockfile`, `dart format --output=none --set-exit-if-changed .`, `dart analyze --fatal-infos`, for api_contract `dart run build_runner build` then `git status --porcelain` must be empty (stale or new generated files fail), `dart run coverage:test_with_coverage`, then a line coverage gate (LH/LF summed from coverage/lcov.info, fails below `MIN_LINE_COVERAGE: 80`, also fails if there are no coverable lines). The result goes to the job summary. Pub cache is cached with actions/cache keyed on the package's own pubspec.lock (decisions.md, T-004).
  - `image`: computes `GIT_SHA` and `APP_VERSION` the same way as server/tool/docker_build.sh; builds linux/arm64 and linux/amd64 from the repo root with `-f server/Dockerfile` and both build args (`push: false`), with the GitHub Actions build cache (`type=gha`, `mode=max`); loads each platform from that cache; smoke tests amd64; sets up QEMU (arm64 only, binfmt image pinned by digest) and smoke tests arm64; finally builds without GIT_SHA on the Docker engine's own builder and checks it fails with the T-009 message and that the transferred context is no bigger than the allowlisted files.
- `server/tool/image_smoke_test.sh` (new): one platform of a loaded image. Checks platform, user `65532:65532`, unpacked size 100 MB or less, `GET /health` 200 within 5 s of `docker run` with status `ok` and the expected version, exit 0 after `docker stop`, exit 78 with no environment. Usable locally too.
- `server/Dockerfile`: the build stage now maps TARGETARCH to Dart's arch and compiles an empty program for the target right after `WORKDIR`, before any repo file is copied. That layer holds the cross-compiler binaries `dart compile exe` downloads into `~/.dart`, depends only on the base image and the target, and so stays cached when code or lockfiles change (T-009 review R1-G3). The real compile step reads the arch from `/opt/dart-target-arch`; its GIT_SHA and APP_VERSION checks are unchanged. Image contents are unchanged (the warm-up output is deleted in the same layer, and only `/out/server` leaves the build stage).
- `server/README.md`: notes on the warm-up layer, the smoke test script, and what CI runs.

Conventions from repo.yml (T-016): `permissions: contents: read`, every action pinned to a full commit SHA with the version in a comment. A `concurrency` group cancels superseded runs of the same ref to save minutes.

**Correction to AC8 ("about 2 kB")**: 1.84 kB is what a warm builder sends: BuildKit transfers only files it has not seen. On a new builder the real context is 86.86 kB, which is the size of the allowlisted files (84,741 bytes of content plus tar headers); the tracked repo is 1,176,304 bytes plus .git, so the ignore file clearly applied. Both numbers appear in the logs: the first build on a fresh runner shows 86.86 kB, the cached loads show 1.84 kB. A fixed 10 kB limit would only have passed because of the warm builder, so the last step builds on the Docker engine's own builder (which has never seen the context) and checks the transfer against the allowlisted size plus 25% and 16 kB: `allowlisted files: 84741 bytes; whole repo: 1176304 bytes; context limit: 121926 bytes`, `ok: build context 86.86kB`. The limit follows the code as it grows.

2. All runs show GitHub's notice that `ubuntu-latest` moves to Ubuntu 26 starting 2026-10-19 (https://github.com/actions/runner-images/issues/14748). Nothing here depends on the Ubuntu version (Dart and Docker images are pinned), so I kept `ubuntu-latest` like repo.yml. Pinning `ubuntu-24.04` is an option if the migration breaks something.
3. `server/Dockerfile` changed (warm-up layer). T-010 is in progress in parallel; if it also edits the Dockerfile, the merge needs care. The change sits right after `WORKDIR /src` and in the compile step's arch lines.

## Proposed decisions

1. CI checks the arm64 image under QEMU on an x64 runner; arm64 runners are not used while the repo is private (they are billed).
2. The coverage gate is 80% line coverage per package, measured from `coverage:test_with_coverage` lcov output, and api_contract's generated files are checked with `build_runner build` plus an empty `git status --porcelain`.
3. The image job runs on every push that touches server/, packages/api_contract/, deploy/, the root analysis_options.yaml, or the workflow, including docs-only server changes (about 1.5 minutes).
