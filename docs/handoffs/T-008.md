**What changed**

New Dart package `server/` (name `boardgame_server`, SDK `^3.13.0`, `publish_to: none`) on shelf + shelf_router (T-005), depending on `api_contract` by `path: ../packages/api_contract` with a committed `server/pubspec.lock` (T-004), and including `../analysis_options.yaml` with `lints` as a dev dependency (T-006).

- `GET /health` returns `HealthResponse(status: "ok", version: <build version>)` as `application/json`, outside /v1. The version is a compile-time define: `dart compile exe -DAPP_VERSION=0.1.0+<sha>`; without it, `0.1.0-dev`. T-009's Dockerfile should pass it.
- Unknown routes (and wrong methods, for example POST /health) return 404 with the `not_found` envelope. `X-Powered-By` is turned off (`poweredByHeader: null`), so no framework text in headers or bodies.
- An error boundary middleware turns any uncaught error into 500 `internal_error` with a fixed message. The error, its stack trace, method, and route template go to the log at error level.
- `errorResponse()` throws `ArgumentError` for `ErrorCode.unknown`, so the server can never send it; inside a handler that becomes a 500 `internal_error` (T-007 decision).
- Config loader `Config.load(Map<String, String>)` reads PORT (1 to 65535) and LOG_LEVEL (`debug`, `info`, `warning`, `error`). It collects every problem first, then throws one `ConfigException` whose message names each variable and its rule, never the value. Empty values count as missing. `runServer` prints that as one JSON line on stderr and returns exit code 78 (EX_CONFIG) before binding a socket. The server reads only the process environment (Compose `env_file` in T-010); it does not parse `.env` itself.
- Logger: one JSON object per line on stdout, keys `ts` (UTC ISO 8601), `level`, `msg`, then fields. The request log middleware writes exactly one `request` line per request with `method`, `route`, `status`, `durationMs`. The route is the template (for example `/v1/games/{bggId}`), recorded by the `Routes` registrar when a route matches; unmatched requests log `<unmatched>` instead of the client-controlled path. No IP, header, query string, or body is ever logged.
- Graceful shutdown: on the first SIGTERM or SIGINT, `server.close()` stops listening and closes idle keep-alive connections; the runner then polls `connectionsInfo()` until in-flight connections finish or 10 s [ASSUMPTION] pass, force-closes the rest (warning line with the count), logs `shutdown complete`, and exits 0. Note: `HttpServer.close()` completes when the listening socket closes, not when connections drain, which is why the runner polls.
- A port that is already in use exits with code 1 and an error line.

### Review, round 1 (code-reviewer): CHANGES REQUIRED

Reviewed `git diff main...HEAD` (9 commits) on 2026-10-12. Overall this is a clean, well-tested skeleton: middleware order is right (request log outside the error boundary, so 500s get exactly one request line), `X-Powered-By` is off, the config loader never echoes values, the server reads only the process environment, `.env` and `.env.*` are git-ignored with `.env.example` committed, the shutdown drain is correct and well tested, and every dependency is BSD, Apache 2.0, or MIT. One must-fix: a request path that bypasses our pipeline and lets shelf print the raw URL to stderr.

**Must fix**

- **R1-M1** server/lib/src/server_runner.dart:69 (`shelf_io.serve`), with shelf-1.4.2 lib/shelf_io.dart:108-131 and 268-290. Requests that fail before or outside our pipeline are logged by shelf itself, not by our Logger. shelf builds the `Request` from `HttpRequest.requestedUri`, which dart:io builds as `Uri.parse("$scheme://$host$uri")` from the client's `X-Forwarded-Proto`, `X-Forwarded-Host`, or `Host` header (dart-sdk lib/_http/http_impl.dart:529-562). A value such as `X-Forwarded-Proto: a b` or `X-Forwarded-Host: [` makes `Uri.parse` throw a `FormatException` whose text contains the whole string, including path and query (`?q=secret`). shelf catches it and writes `ERROR - <local time>`, `Error parsing request.`, the exception text, and a stack trace to stderr as plain multi-line text, then answers 500 `text/plain` "Internal Server Error". The same printer handles shelf's `catchTopLevelErrors` zone ("Asynchronous error") and `_logError`, which writes `method path?query`. Why it matters: AC8 and the README say a query string and header values are never logged; this path logs both, breaks the one-JSON-object-per-line format, writes no `request` line (AC7), and returns a body that is not the error envelope (AC2/AC3 spirit). Caddy (T-010) probably rewrites the X-Forwarded headers, but the server must not depend on that, and later handlers could reach the zone printer with stray async errors. Found by reading code; I could not run a socket probe (reviewer has no write access for a scratch test). Suggested fix: bind the `HttpServer` yourself (`HttpServer.bind`) and handle each `HttpRequest` in our code: read `request.requestedUri` inside try/catch first; on failure write our own JSON response (404 `not_found` or 500 `internal_error`; a `bad_request` code would be an additive api_contract change, so ask first) and log one `request` line with `route: <unmatched>`; otherwise call `shelf_io.handleRequest(request, handler, poweredByHeader: null)`. Wrap the listener in `runZonedGuarded` that logs only through our Logger. Add a real-socket test that sends a raw request with `X-Forwarded-Host: [` and `?q=secret` (via `Socket`, since `HttpClient` may refuse the header) and asserts: response is the JSON envelope, captured stdout/stderr lines are all JSON, and none contains `secret` or the header value.

**Should fix**

- **R1-S1** server/lib/src/http/middleware.dart:50 and server/lib/src/logging/logger.dart:79. `errorBoundary` logs `error.toString()` verbatim. Today no handler parses input, but from T-018 on a `FormatException` from `int.parse` or `jsonDecode` carries the raw input (bggId, barcode, body snippet), and HTTP client exceptions (dio) include the upstream URL, which can contain the user's search query or an API key. Why: a future privacy or secret leak through the one field the request log does not control. Suggested fix: log `errorType: error.runtimeType.toString()` plus the stack trace, and include the message only for exception types we own; or add a small redactor and document the rule in the Logger doc comment and the server README so later tickets follow it. AC3 is still met (the error is identified and the stack trace logged).
- **R1-S2** server/lib/src/server_runner.dart:20 (grace 10 s) with T-010. `docker stop` and Compose send SIGKILL 10 s after SIGTERM by default, so a drain that uses the full 10 s grace is killed before it force-closes and logs `shutdown complete`, and the exit code is 137, not 0 (AC9 in production). Suggested fix: add to Proposed decisions that T-010 sets `stop_grace_period: 15s` (or more) on the server service, and mention it in server/README.md under Shutdown so the two numbers are kept in step.

**Suggestions**

- **R1-G1** server/lib/src/app.dart:36 and server/lib/src/http/routes.dart:53. For T-066 (attestation on every /v1 route) and T-020 (per-IP limits), wrapping each handler in `Routes` means an unmatched `/v1/...` path returns 404 without attestation or rate limiting, and a new route can forget the wrapper. Consider letting `Routes` take a `Middleware` applied to every route it registers, or mounting a /v1 sub-router behind its own `Pipeline` with a /v1 not-found handler, so every /v1 request, matched or not, passes the same checks. Rate limiting should sit inside `requestLog` (so 429s are logged) and outside `errorBoundary`.
- **R1-G2** server/lib/src/server_runner.dart:69. Set `server.idleTimeout` explicitly (dart:io default is 120 s) and note a request body size limit for the first ticket that reads a body; cheap hardening for a server on a small VM, even behind Caddy.

Open question 2: `<unmatched>` is the right call for privacy. Open question 3: the in-process real-socket drain test plus the real-process SIGTERM test is enough for AC9.

## Open questions

1. AC7 says every request writes one line. Request lines are `info` (or `error` for 5xx), so with LOG_LEVEL=warning or error, 2xx to 4xx lines are dropped. Production should run LOG_LEVEL=info. Is that acceptable, or should request lines ignore LOG_LEVEL?
2. For unmatched requests the log says `"route":"<unmatched>"` rather than the raw path, because the path is client-controlled and could carry anything. That hides scanner traffic patterns in logs. OK?
3. AC9's in-flight drain is proven in-process with an injected signal; the real-process SIGTERM test checks stop-accepting and exit 0 but has no in-flight request, because the production binary has no slow route and I did not want a test-only route reachable in production. QA may want to judge whether that split is enough.
4. (Round 2) A request whose URL cannot be built (bad Host or X-Forwarded-Host) gets 404 `not_found`, since the contract has no `bad_request` code. Should api_contract add `bad_request` (400) as an additive /v1 change? That would be a contract change for the flutter-developer (the app would only need to treat it as a generic error).

## Proposed decisions

1. Config errors exit with code 78 (EX_CONFIG); bind errors exit with 1. The server reads only process environment variables (Compose `env_file`), never a `.env` file itself.
2. The build version is the compile-time define `APP_VERSION` (default `0.1.0-dev`); T-009 passes `<pubspec version>+<short git sha>`.
3. Log retention [ASSUMPTION]: target 7 days. Logs go to stdout only, never to files in the container, and nothing is shipped off the VM. Docker log drivers rotate by size, not age, so T-010 sets `max-size: 10m` and `max-file: 3` (30 MB cap; a request line is about 150 bytes, so roughly 200,000 requests). If low traffic would keep lines longer than 7 days, T-010 needs a time-based rule as well (for example the journald driver with a `MaxRetentionSec` setting on the VM); I will confirm the option against official docs in T-010.
4. Request log fields are fixed to `method`, `route` (template or `<unmatched>`), `status`, `durationMs`. New request fields need a privacy check in review.
5. (Round 2) Error log rule: `errorType`, a redacted `error` from `describeError`, and `stack`; new code never puts request data, tokens, or upstream bodies into exception messages (server README, Logs).
6. (Round 2) The server binds its own HttpServer (`bindAndServe`) and never uses `shelf_io.serve`, so no output reaches stdout or stderr except our JSON lines. Idle keep-alive timeout 65 s; T-010 sets Compose `stop_grace_period: 15s` and a Caddy upstream keep-alive shorter than 65 s.
7. (Round 2) /v1 guards (T-020 rate limit, then T-066 attestation) go in `buildApp(v1Middleware: ...)`, inside the error boundary.
