**What changed**

- Dependencies (licenses checked in the pub cache): `mobile_scanner` 7.4.2 (BSD-3-Clause; ML Kit on Android approved 2026-10-11, MLKIT-01 to MLKIT-08), `permission_handler` 12.0.1 with `permission_handler_android` 13.0.1, `_apple` 9.6.2, `_platform_interface` 4.4.1, `_html` 0.1.4+1, `_windows` 0.2.2 (all MIT). Not 13.x: its Android package 14.x requires compileSdk 37, which failed the CI Android build (run 38640219036) and is above what our Android Gradle plugin 9.1 supports; moving to compileSdk 37 is a separate decision. permission_handler is needed because mobile_scanner cannot tell denied, permanently denied, and restricted apart, and cannot open the app's settings page. Native dependencies pulled in on Android: `com.google.mlkit:barcode-scanning` 17.3.0 (bundled model, Google terms, approved) and CameraX 1.6.1 (Apache 2.0).
- `app/lib/features/scanner/domain/`: `barcode_detection.dart` (raw text plus the reported symbology, null for anything but UPC-A, EAN-13, EAN-8), `scan_filter.dart` (`ScanFilter`: symbology first, then `Barcode.parse`, then the 2 s same-code window keyed on `gtin13`; `reset()` when the user comes back; monotonic `Stopwatch` factory injected), `camera_permission.dart` (`CameraPermission` enum and the `CameraPermissionRepository` interface returning `Result`).
- `app/lib/features/scanner/data/`: `permission_handler_camera_permissions.dart` (repository plus keepAlive provider; plugin errors become `UnexpectedFailure`, logged by type only), `scanner_detection_mapper.dart` (mobile_scanner `BarcodeCapture` to domain detections; the camera is asked for the three formats only, and anything else maps to a null format anyway).
- `app/lib/features/scanner/presentation/`:
  - `scanner_camera.dart`: `ScannerCamera` interface, `MobileScannerCamera` (mobile_scanner controller with `autoStart: false`; maps torch state and start errors; never throws), and the providers `scannerCameraFactoryProvider` and `scanStopwatchFactoryProvider` that tests override.
  - `scan_session.dart`: `ScanSession` (ChangeNotifier state machine: starting, requesting, scanning, detected, denied, permanentlyDenied, restricted, unavailable; one step at a time, so a lifecycle change during a permission request or a camera start is applied when that step ends) and `CameraPromptShownProvider` (keepAlive: the prompt shows once per app run).
  - `scan_screen.dart`: the screen. The camera runs only while the route is current, the tab is selected (go_router's TickerMode), and the app is resumed (`AppLifecycleListener`); visibility changes apply after the frame. Detection: haptic (`HapticFeedback.lightImpact`), polite announcement `scanner.success`, the frame turns primary with a check for 300 ms (no fill with reduce motion), then the lookup result is pushed through `OpenOnce`. Layouts: compact column; medium buttons capped at 280 dp; expanded preview capped at 720 dp; phone landscape (wider than tall and under 600 dp tall) puts the preview on the left 60% and the actions plus hint in the right column. The action bar keeps the preview at 40% of the height or more and scrolls past that.
  - `scanner_viewfinder.dart`, `torch_toggle.dart`, `scan_action_bar.dart`, `permission_panel.dart`: the four components from components.md.
- `app/lib/app/`: the router wires `onSearch` (`goBranch` to Search, like the bar) and `onScanned` (push `lookupResultPath(scan, barcode)`); `AppDestination.screenTitle`; `AppShell.didUpdateWidget` announces the new destination's title on every destination change (bar, rail, the Search button, Back to Scan; AC17).
- `app/lib/core/widgets/placeholder_body.dart`: the `actions` slot added for the Scan placeholder in T-031 is gone (no user left).
- `app/lib/l10n/app_en.arb`: all `scanner.*` keys the screen uses, plus `common.retry` and `common.openSettings`. `scanner.iosUsageDescription` lives in Info.plist, not the arb.
- `app/ios/Runner/Info.plist`: `NSCameraUsageDescription` with the copy.md text. Under Swift Package Manager, permission_handler_apple turns on its camera code (`PERMISSION_CAMERA`) because this key exists (its README); no Podfile change is needed.
- `app/android/app/src/main/AndroidManifest.xml`: `CAMERA` permission and `android.hardware.camera` with `required="false"` (mobile_scanner's manifest declares the same; repeated so ours states it).
- `.github/workflows/app.yml`: a "Report APK size" step in the Android job writes the debug APK size and its `.so` files to the job summary (AC16).
- Tests: `test/helpers/fake_scanner.dart` (`FakeScannerCamera`, `FakeCameraPermissions`, `ScannerFakes`); `pumpApp` and the new `testApp(fakes)` install the fakes by default, so no test touches a camera plugin. The golden tests and the T-031 offline test now use them.

**APK size (AC16)**

The "Report APK size" step of the Android job lists the debug APK size and every `.so` file. App.yml run 38641218747 (commit 4cdabc7): debug APK 188,693,518 bytes in total (all three ABIs, debug engine, so not a store size). Native libraries the scanner adds, uncompressed per ABI:

| Library | arm64-v8a | armeabi-v7a | x86_64 |
|---|---|---|---|
| libbarhopper_v3.so (bundled ML Kit barcode model) | 4,946,720 | 3,244,440 | 5,909,280 |
| libimage_processing_util_jni.so (CameraX) | 32,528 | 24,448 | 49,416 |
| libsurface_util_jni.so (CameraX) | 4,896 | 3,460 | 4,912 |

So the bundled model costs about 4.9 MB uncompressed on a 64-bit ARM phone (inside the 3 to 10 MB range of MLKIT-06), plus the ML Kit and CameraX Java code, which this step does not separate. I could not record a before/after delta: building a baseline needs either a local Gradle build (C: has about 9 GB free) or a scratch branch from main with the same step, and pushing that scratch branch was refused by the permission system. Option for the orchestrator: allow a scratch branch push (main plus commit "T-030: report debug APK size"), or accept the per-ABI `libbarhopper_v3.so` size as the ML Kit cost. A debug APK is not the store size either; a release App Bundle measurement belongs with T-036.

### Open questions

1. Action stacking at 200% text: scanner.md section 2 says stack "if the labels would wrap past 2 lines", but the golden list says "Actions stacked" for the 200% golden, where Roboto wraps "Search by title" to exactly 2 lines. I stack as soon as a label wraps, which matches the golden note. UX: confirm, or change the section 2 wording.
2. Phone landscape: the actions come first in the right column and the hint below them, so 200% text cannot push the actions out of view (scanner.md section 1). Section 2 lists "hint text and the two action buttons" without an order. UX: confirm.
3. The permission prompt shows once per app run, not once per install: on Android a "denied" status cannot tell "never asked" from "denied once", so the next app run asks once more (Android itself stops showing the prompt after the second denial). Storing a flag would need a settings store that does not exist yet. PM or UX: is once per run acceptable?
4. Dark theme scanning golden: over the dark placeholder the scrim, hint pill (surface), and torch toggle (surface) are close in tone. On a real camera image the pill and toggle stand out; UX may want a different role for the toggle background in dark.

### Proposed decisions

1. permission_handler (MIT) is the camera permission source; mobile_scanner is used with `autoStart: false` and only after the permission is granted.
2. Widget tests use `ScannerFakes` through `pumpApp`/`testApp`; any test that pumps the whole app must use them (real plugin channels never answer in fake async, which leaves the scanner in "starting").
3. Every destination change announces the destination's screen title from the shell (`AppShell.didUpdateWidget`), not only taps on the bar or rail.
4. The camera runs only while the scanner's route is current, its tab is selected, and the app is resumed.
5. The debug APK size and native libraries are reported in the Android job summary on every run.
