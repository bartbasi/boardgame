### Review (code-reviewer): CHANGES REQUIRED

Scope: `git diff main...HEAD` (11 commits, merge base f16db51). The ticket text on main is identical to the branch. Overall this is careful work: the domain stays pure, the plugins sit behind interfaces with good fakes, the session is a clear one-step-at-a-time state machine, and the tests are thorough. Two must-fix items concern store and platform behavior that widget tests cannot see.

**Must fix**

- R1-M1. `app/lib/features/scanner/presentation/scan_session.dart:42-58, 215-222`. On Android a user who denied the camera once gets the system prompt again at the next launch.
  - Why it happens: the prompt is "once per app run" (open question 3), and Scan is the start destination, so the next launch prompts again before any tap. That is the case AC1 rules out ("never appears at app start"; only the first open asks). It also runs against "nothing may block or require a tap", because the system dialog is modal.
  - It needs no settings store. On Android, `Permission.camera.shouldShowRequestRationale` (permission_handler 12.0.1, `lib/permission_handler.dart:95`) is true after one denial and false before any request. So "denied, never asked" and "denied once" can be told apart. After "don't ask again", permission_handler's `status` already returns permanentlyDenied across runs: `PermissionUtils.determineDeniedVariant` keeps a SharedPreferences flag. On iOS, never asked and denied already differ (iOS reports permanentlyDenied after the first answer).
  - Fix:
    1. Have the repository report the difference, for example a `deniedBefore` value or `Result<bool> wasDeniedBefore()` in `CameraPermissionRepository`, mapped from `shouldShowRequestRationale` in `permission_handler_camera_permissions.dart`.
    2. Prompt automatically only for "denied and never asked". Keep `CameraPromptShown` for the current run.
    3. Add a fake flag and a test: a new run with "denied before" shows the Denied panel and `requestCount` stays 0.
  - If PM and the user prefer to accept once per run, record that in decisions.md and reword AC1. Then this item drops to a should fix.
- R1-M2. `app/android/app/src/main/AndroidManifest.xml:13`. AC15 is not met as intended.
  - Only `android.hardware.camera` is declared not required. Android's "Permissions that imply feature requirements" table (https://developer.android.com/guide/topics/manifest/uses-feature-element, the page GPLAY-01 cites, which says "implies camera hardware features" in the plural) lists the CAMERA permission as implying both `android.hardware.camera` and `android.hardware.camera.autofocus`.
  - Without `<uses-feature android:name="android.hardware.camera.autofocus" android:required="false"/>`, Google Play still treats autofocus as required. So devices without a camera (or without autofocus) are filtered out, and the purpose of AC15 is lost. Neither mobile_scanner's manifest nor ours declares it.
  - Fix:
    1. Add the line next to the existing one.
    2. Extend `test/platform/camera_declarations_test.dart`.
    3. In the AC15 manual check, also run `aapt dump badging` on the APK and confirm no `uses-implied-feature` line for the camera says required.
  - PM: add the autofocus fact to GPLAY-01 in api-research.md with its source and date.
  - Because this changes a manifest, it needs a new manual app.yml run with the iOS build (decision 2026-10-15).

**Should fix**

- R1-S1. iOS camera permission is compiled in only if Swift Package Manager finds the Info.plist key. permission_handler_apple 9.6.2 under SPM turns on `PERMISSION_CAMERA` only when its package manifest finds `NSCameraUsageDescription` in our Info.plist. If discovery fails, the camera code is compiled out silently and every check reports denied (its README, "Builds started from Xcode.app", and the note that Xcode discards the manifest warning). A green iOS build does not prove the macro was on.
  - Fix: in the iOS job of `.github/workflows/app.yml`, after `flutter build ios`, run the README's check (`PERMISSION_HANDLER_VERBOSE=1 swift package --manifest-cache none --package-path ios/Flutter/ephemeral/Packages/.packages/permission_handler_apple dump-package`) and fail unless it reports `PERMISSION_CAMERA` as 1.
  - At minimum, add "the iPhone shows the system prompt (not straight to Denied)" to the AC1 TestFlight check.
- R1-S2. `app/lib/features/scanner/presentation/scan_session.dart:288-296`. After `onOpen`, the timer sets the phase back to scanning while `_active` is still true. The screen only goes inactive in a post-frame callback after the push builds. A different valid code that arrives in that gap passes the filter, and fires a second haptic and a second "Barcode ... read. Looking up the game." announcement for a code that never opens (OpenOnce or the cancelled timer stops the navigation).
  - QA's test "a different code right after the lookup opened (route not yet current)" checks only the number of results, so it passes.
  - Fix: after `onOpen`, stay in `detected` (no detections accepted) until `setActive(false)` arrives. If the open was ignored (`isOpening`), go back to scanning only when the route is current again. Then assert haptics and announcements in that test.

**Checked, no finding**

- Architecture: domain files have no Flutter or plugin imports. `CameraPermissionRepository` is in domain, its implementation and the plugin mapper are in data, and errors become `UnexpectedFailure` logged by type only, in debug only. `ScannerCamera` is an interface; `MobileScannerCamera` lives in presentation because it builds the preview widget, which is acceptable. No BGG, eBay, or GameUPC hosts in app/lib.

On dispose, the subscription is cancelled, the listeners removed, and the controller disposed. `start` waits for the preview to attach (mobile_scanner waits up to 500 ms) and never throws. After a stop, the real controller reports torch off rather than unavailable (`_stop`, line 286), and the session handles both.
