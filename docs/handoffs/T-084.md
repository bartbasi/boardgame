### Developer notes (backend-developer)

**What changed**

- `server/lib/src/config/ebay_account_deletion_config.dart`: `EbayAccountDeletionConfig.load` reads `EBAY_ACCOUNT_DELETION_VERIFICATION_TOKEN` and `EBAY_ACCOUNT_DELETION_ENDPOINT_URL`. Both or neither: with neither, the endpoint is off (404) and startup logs `eBay account deletion endpoint` with `enabled: false`; with one, or an invalid one, startup exits 78 with the usual one-line problem list (variable names and rules, never values). `toString` redacts the token.
  - Token (AC3): `^[A-Za-z0-9_-]{32,80}$` (ASCII only).
  - URL (AC4): at most 2,048 characters [ASSUMPTION]; scheme `https`; no user info, query, or fragment; path exactly `/ebay/marketplace-account-deletion`; host either a public IP literal (rejects loopback, 0/8, 10/8, 100.64/10, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/4 and above; IPv6 only 2000::/3 outside 2001:db8::/32; IPv4-mapped judged as IPv4) or a DNS name with at least two labels and a letter-only (or `xn--`) top-level label, not `localhost` or `*.localhost`. The letter-only TLD rule also rejects forms like `127.1`, `0x7f.1`, `2130706433`, and `10.0.0.1.` that some resolvers read as IPs. No DNS lookup is made (a public name that resolves to a private address is not detected; eBay's own check would fail). The path rule is my addition: it makes sure the URL hashed into the response is the URL that reaches this route.
  - The URL is kept exactly as written (only surrounding whitespace trimmed) and hashed as is (EBAY-17).
- `server/lib/src/ebay/account_deletion.dart`:
  - `challengeResponse(code, token, url)`: SHA-256 over the UTF-8 concatenation, lowercase hex (`crypto`, already a dependency).
  - GET with exactly one non-empty `challenge_code` (at most 1,024 characters [ASSUMPTION]): 200, `content-type: application/json`, `cache-control: no-store`, body `{"challengeResponse":"<hex>"}` from `jsonEncode` (no BOM). The decoded query value is hashed. Anything else: 400 with the error envelope shape and the server-only code `invalid_challenge_code` (not added to api_contract; the app never calls this route).
  - POST: the body is read in chunks and dropped, never parsed, stored, or logged, then 204 with no body. Reading it matters: dart:io closes a connection whose request body was left unread (http_impl.dart checks `incoming.fullBodyRead`), which could make Caddy see a reset while still sending. Over 64 KiB [ASSUMPTION]: 413 `payload_too_large` (by Content-Length, or while reading); a body that stalls 10 s [ASSUMPTION]: 408 `request_timeout`. The `x-ebay-signature` header is not checked (proposed decision 2).
  - The file imports no database, file, or logger code (a test checks the import list).
- `server/lib/src/app.dart`: `buildApp(ebayAccountDeletion:, ebayMiddleware:)`. When configured, `/ebay` is mounted on the root router beside /v1, behind its own middleware list, so the /v1 guards (rate limit now, attestation in T-066) never run for it (AC5). Request log and error boundary still wrap it.
- `server/lib/src/server_runner.dart`: loads the new config together with the others (one line names every problem), builds a second `RateLimiter` (60 per minute [ASSUMPTION], 10,000 tracked IPs [ASSUMPTION], well under 1 MB) with its own sweep timer, shares the `ClientAddressResolver` (Caddy's X-Forwarded-For rule from T-020), and logs `eBay account deletion endpoint` `{enabled}` at startup.
- `server/.env.example`: both variables with low-entropy placeholders that pass validation. `deploy/docker-compose.yml`: optional pass-through `${VAR:-}`. `deploy/.env.example`: the two lines commented out, because server.yml's compose check requires every uncommented variable there to be a `${VAR:?}` guard. `server/README.md`: routes and middleware.

## Open questions

1. Signature verification (EBAY-15): eBay says the developer "should" verify `x-ebay-signature`. Verifying needs the Notification API getPublicKey call with an application token, which is a production eBay call that EBAY-10 forbids before this endpoint is live, and it would add no protection for data we do not hold. I did not implement it (proposed decision 2). Does the user agree, or should a later ticket add it once production credentials exist?
2. Rate limit vs. eBay bursts: eBay may send up to 1,500 notifications a day (EBAY-16) from unpublished addresses. If a burst exceeds 60 a minute from one address, the extra ones get 429 and eBay resends later (it resends until acknowledged). After 24 hours of failures eBay marks the URL down. I think 60 [ASSUMPTION] is fine, but PM may prefer a higher number (for example 300) for this route.
3. Should the endpoint become required (startup fails without it) once eBay production credentials exist? I propose yes, in the ticket that adds the eBay credentials (T-052 or T-053), so the server can never call eBay production without it (proposed decision 1).
4. EBAY-17: eBay gives no normalization rules for the URL in the hash. I hash the configured string exactly; whoever does AC7 must paste the identical string into the portal and the VM's deploy/.env.

## Proposed decisions

1. T-084: the two `EBAY_ACCOUNT_DELETION_*` variables are optional as a pair until the eBay client exists; the ticket that adds production eBay credentials makes them required whenever those credentials are set.
2. T-084: notifications are acknowledged without verifying `x-ebay-signature`, because we store no eBay user data and verification needs a production eBay call (EBAY-10, EBAY-15). Revisit if we ever store eBay user identifiers.
3. T-084: the route is `/ebay/marketplace-account-deletion` outside /v1, and the configured URL's path must equal it. Server-only error codes on this route (`invalid_challenge_code`, `payload_too_large`, `request_timeout`) are not added to api_contract.
4. T-084: notification bodies over 64 KiB get 413 and bodies that stall 10 s get 408 [ASSUMPTION]; challenge codes over 1,024 characters get 400 [ASSUMPTION].
5. T-055 and any later migration: no seller, buyer, eBay username, user id, or EIAS column, enforced by `test/ebay/no_ebay_user_data_test.dart`. Storing one would need real deletion handling first (EBAY-18).
