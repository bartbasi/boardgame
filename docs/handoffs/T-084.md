- `server/lib/src/ebay/account_deletion.dart`:

  - GET with exactly one non-empty `challenge_code` (at most 1,024 characters [ASSUMPTION]): 200, `content-type: application/json`, `cache-control: no-store`, body `{"challengeResponse":"<hex>"}` from `jsonEncode` (no BOM). Reading it matters: dart:io closes a connection whose request body was left unread (http_impl.dart checks `incoming.fullBodyRead`), which could make Caddy see a reset while still sending. Over 64 KiB [ASSUMPTION]: 413 `payload_too_large` (by Content-Length, or while reading); a body that stalls 10 s [ASSUMPTION]: 408 `request_timeout`. The `x-ebay-signature` header is not checked (proposed decision 2).

**Observations (not bugs)**
- HEAD to the challenge route answers 200 with an empty body, because shelf_router answers HEAD for a GET route. Nothing leaks. Other methods (PUT, DELETE, PATCH, OPTIONS, TRACE) are refused.
- Equivalent spellings of the right URL pass validation because Dart normalizes them: an empty user info (`https://@host/...`), dot segments (`/ebay/./marketplace-account-deletion`, `/x/../ebay/...`), `%2D` for `-`, an empty port (`host:/...`), and `%61` in the host. The raw string is what gets hashed, so a mismatch would show up at the portal check (AC7), not silently. Pinned in a test.
- Internal-looking DNS names pass (`.local`, `.internal`, `.lan`, `.corp`) and so do 6to4 and Teredo IPv6 prefixes inside 2000::/3, because no lookup is made. The ticket only asks for localhost and internal IP addresses. Pinned in a test.
- `+` in a challenge code is read as a space (form decoding). eBay's documented example is `123`, and a real `+` would be percent-encoded, so this is fine.
- A chunked POST over 64 KiB gets 413 as soon as the limit is passed, and the connection is closed. On Windows the client can see a reset instead of the 413. The test accepts either.
- The developer's guard regex does not list `account`, `feedback`, `email` and similar words; my wider scan does, and passes today. Consider widening the guard when T-055 adds the listing cache.

## Open questions

1. Signature verification (EBAY-15): eBay says the developer "should" verify `x-ebay-signature`. Verifying needs the Notification API getPublicKey call with an application token, which is a production eBay call that EBAY-10 forbids before this endpoint is live, and it would add no protection for data we do not hold. I did not implement it (proposed decision 2). Does the user agree, or should a later ticket add it once production credentials exist?
2. Rate limit vs. eBay bursts: eBay may send up to 1,500 notifications a day (EBAY-16) from unpublished addresses. If a burst exceeds 60 a minute from one address, the extra ones get 429 and eBay resends later (it resends until acknowledged). After 24 hours of failures eBay marks the URL down. I think 60 [ASSUMPTION] is fine, but PM may prefer a higher number (for example 300) for this route.
3. Should the endpoint become required (startup fails without it) once eBay production credentials exist? I propose yes, in the ticket that adds the eBay credentials (T-052 or T-053), so the server can never call eBay production without it (proposed decision 1).
4. EBAY-17: eBay gives no normalization rules for the URL in the hash. I hash the configured string exactly; whoever does AC7 must paste the identical string into the portal and the VM's deploy/.env.

## Proposed decisions

1. T-084: the two `EBAY_ACCOUNT_DELETION_*` variables are optional as a pair until the eBay client exists; the ticket that adds production eBay credentials makes them required whenever those credentials are set.
2. T-084: notifications are acknowledged without verifying `x-ebay-signature`, because we store no eBay user data and verification needs a production eBay call (EBAY-10, EBAY-15). Revisit if we ever store eBay user identifiers.
3. T-084: the route is `/ebay/marketplace-account-deletion` outside /v1, and the configured URL's path must equal it. Server-only error codes on this route (`invalid_challenge_code`, `payload_too_large`, `request_timeout`) are not added to api_contract.
4. T-084: notification bodies over 64 KiB get 413 and bodies that stall 10 s get 408 [ASSUMPTION]; challenge codes over 1,024 characters get 400 [ASSUMPTION].
5. T-055 and any later migration: no seller, buyer, eBay username, user id, or EIAS column, enforced by `test/ebay/no_ebay_user_data_test.dart`. Storing one would need real deletion handling first (EBAY-18).
