#### What changed

1. Function body mode only in CREATE FUNCTION or PROCEDURE (R3-S1). `scanTransactionControl` (server/lib/src/db/transaction_control.dart) enters `BEGIN ATOMIC` mode only when the statement starts `CREATE FUNCTION`, `CREATE PROCEDURE`, `CREATE OR REPLACE FUNCTION`, or `CREATE OR REPLACE PROCEDURE` (token positions 1 or 3, the grammar's `CREATE opt_or_replace FUNCTION|PROCEDURE`), and only outside parentheses. The parenthesis rule is stricter than the reviewer's suggestion: `CREATE FUNCTION f(begin atomic) ...` (argument `begin` of a type named `atomic`) and `RETURNS TABLE (begin atomic)` are valid SQL that would otherwise enter body mode. A trigger's `EXECUTE FUNCTION` is at a later position, so it does not count.
2. Unclosed body refused (R3-S1, AC4). The scan returns a record `({String? statement, bool unclosedBody})`; `unclosedBody` is true when the SQL ends inside `BEGIN ATOMIC` (CASE nesting included). `validateMigrations` throws `MigrationStateException`: `migration N (name) has a BEGIN ATOMIC function body that is not closed; end it with END`. No SQL in the message. `findTransactionControl` keeps its signature and returns `.statement`.
3. `standard_conforming_strings` reset per migration (R3-G1, AC6). `migrate` runs `SET standard_conforming_strings = on` on its connection right before each migration's transaction, inside the same try, so a failure there is reported as that migration's `MigrationFailedException`.
4. Optional R3-G2, fixed. A digit starts a number token (digits, letters, `_`, `.`), and a `$` reached at the top of the loop always tries to open a dollar quote (the old "previous character is an identifier character" check is gone: identifiers consume their own `$`, so the check only ever fired after numbers and after a closing dollar quote). This matches scan.l for `1$$`, `1.5$$`, `$1$$`, `0x1F$$`, `1e5$$`. Taking letters into the number is harmless: PostgreSQL 15 and later reject a number followed by letters as trailing junk. The one remaining difference I know of is two adjacent dollar quotes (`$a$x$a$$b$`), which PostgreSQL rejects as a syntax error; since the server parses the whole simple query string before running any of it, nothing runs in that case. The scanner's doc comment says so.
5. Docs (AC7): the `Migration` doc comment (server/lib/src/db/migration.dart) and server/README.md "Migrations" both state the two new rules.

**Observations (not bugs)**
- `SELECT 1 AS end` inside a body (valid SQL, since AS accepts any keyword) makes the scanner close the body early, and the real END is then refused as a statement start. `AS case` leaves the body open, which is refused as unclosed. Both are false positives in the safe direction and only affect our own reviewed migrations. Pinned in a test.
- The adjacent dollar-quote case the developer documents (`$a$x$a$$b$`) is PostgreSQL's syntax error; the scanner has no hole there.
- `SET standard_conforming_strings = on` is the only session state reset between migrations. A migration that changes `search_path`, `role`, or similar leaks it to the next migration on the same connection. Out of scope for T-101; worth a line in T-019's rules if it ever matters.
- The ordering that makes the reset sufficient: PostgreSQL parses the whole simple-query string before running any of it, so a `SET standard_conforming_strings = off` inside a migration cannot change how that same migration's text is lexed, only the next one's. The per-migration `SET ... = on` therefore covers every case.

**Must fix**

- **R1-M1: body mode still counts `CASE` and `END` as keywords, so a label named `case` makes the scanner's body outlive PostgreSQL's, and a later `END` or COMMIT is not refused.** server/lib/src/db/transaction_control.dart, the `atomicDepth` branch (`else if (word == 'CASE') atomicDepth++; else if (word == 'END') atomicDepth--;`). QA judged `AS case` a safe-direction false positive because a single body is then refused as unclosed. That holds only when nothing later brings the count back to zero. Probe (scratch script calling `scanTransactionControl`, outside the repo), with `f` = `CREATE FUNCTION f() RETURNS int LANGUAGE sql BEGIN ATOMIC`:
  - `f SELECT 1 AS case; END; END; SELECT 1;` gives `(statement: null, unclosedBody: false)`. For PostgreSQL the body ends at the first END, and the second `END;` is a COMMIT that runs inside the migration's transaction. This is T-019-B1 again.
  - `f SELECT 1 AS case; END; COMMIT; CREATE FUNCTION g() ... BEGIN ATOMIC SELECT 1; END;` gives null: the second body's END closes the scanner's phantom depth.
  - `SELECT t.case FROM t` (a column `"case"`, attr_name is a ColLabel) inside the body does the same.

  `SELECT 1 AS case` is valid: AS takes any keyword, reserved ones included, as QA notes for `AS end`. Whether CASE and END are also bare labels (`SELECT 1 case`) I could not check without PostgreSQL, which is one more reason not to rely on recognizing labels.

  Suggested fix, which matches the grammar exactly and is simpler: in body mode, stop counting CASE and END. PostgreSQL's body is `BEGIN ATOMIC routine_body_stmt_list END`, where the list is `stmt ';' stmt ';' ...`. So the closing END is always the first token right after `ATOMIC` or right after a `;` inside the body, and a CASE expression's END can never be in that position, because a CASE cannot contain `;`. Track "first token of a body statement" (reset after ATOMIC and after each `;` in body mode). The body closes when that token is END. `AS end`, `AS case`, `t.case`, and nested CASE then need no special handling, and QA's `AS end` false positive goes away too.

  Add the three probes above as unit tests, plus one real-PostgreSQL case for `... AS case; END; END;` when Docker or CI is available. Update the doc comment ("with `CASE ... END` nesting inside it") and the README if they mention nesting.
