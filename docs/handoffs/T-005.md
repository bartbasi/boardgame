#### 4. Middleware for attestation and per-IP rate limits

Neither framework ships attestation or rate limiting. In both, they are a few lines of our own middleware (spike: `server/spike/shelf_health/lib/app.dart`, `server/spike/dart_frog_health/lib/rate_limit.dart`). The real verification work (Play Integrity token decode, App Attest certificate chain and counter checks, per docs/api-research.md B7, APPLE-13, GPLAY-09) is framework-independent code that M5 tickets write either way.

- **Scoping.** We need `/health` open, `/v1/*` behind attestation, and (per B7) probably a session-start endpoint that verifies attestation and issues a short-lived token used by the other `/v1` routes.
  - shelf: explicit. `Router().mount('/v1/', Pipeline().addMiddleware(attestation(...)).addHandler(v1Router))`, and `/health` sits on the outer router. Ordering is visible in one file.
  - dart_frog: by folder. `routes/_middleware.dart` applies to everything, `routes/v1/_middleware.dart` to `/v1` only. Also works, but the order is spread across files and resolved by generated code.
- **Client IP.** shelf: `request.context['shelf.io.connection_info']` as `HttpConnectionInfo`. dart_frog: `context.request.connectionInfo`. Same data. Behind Caddy both see Caddy's address, so the real limiter must read `X-Forwarded-For` only when the peer is the trusted proxy (T-008 or the rate limit ticket).
- **State.** A limiter keeps counters across requests. In dart_frog the generated `server.dart` calls `buildV1Handler()(context)` on every request, which rebuilds nested pipelines and calls nested `_middleware.dart` functions per request (seen in the generated `build/bin/server.dart`). Any state must therefore live in a top-level variable or a provider, not in the middleware function. In shelf the pipeline is built once at startup and state lives in the middleware closure, which also makes it easy to inject a clock for tests.
- **Methods.** dart_frog's generated router registers every route with `.all(...)`, so each handler must check `context.request.method` and return 405 itself. shelf_router registers `.get(...)` and answers other methods with 404 by default; we would still add a 405 handler if we want typed errors.

#### 5. How endpoints are tested

- **shelf:** a `Handler` is a function `Request -> Response`. Tests build the whole app with injected fakes and call it with a real `Request` object: no server, no socket, no mocks. The spike test (`server/spike/shelf_health/test/app_test.dart`) covers /health open, /v1 without attestation (401), with attestation (200), a path parameter error (400), the per-IP limit (429 for the 4th request, other IP unaffected), and window reset with an injected clock. 6 tests, all pass. The full pipeline including routing and middleware order is exercised.
- **dart_frog:** the official guide (https://dart-frog.dev/basics/testing, read 2026-10-12) recommends package:test plus mocktail: call each route's `onRequest` with a mocked `RequestContext`, and test middleware by wrapping a dummy handler. The spike test (`server/spike/dart_frog_health/test/routes/routes_test.dart`) does that: 4 tests pass. Routing and the middleware chain from `_middleware.dart` files are not exercised by these unit tests, because they live in generated code; testing them needs `dart_frog build` first or an end-to-end test against a running server. A `dart_frog_test` package exists (0.1.2, 2025-10-02, 3 likes) but the official testing page does not mention it.

#### 6. AOT compilation with `dart compile exe`

Both compile to a native executable and run from `FROM scratch` with the official image's `/runtime/` folder (the pattern in https://hub.docker.com/_/dart).

- shelf: `dart compile exe bin/server.dart`. Nothing else.
- dart_frog: `dart_frog build` first generates `build/` (a `bin/server.dart`, a copy of the routes, a pubspec, and a Dockerfile); then `dart compile exe build/bin/server.dart`. The default generated Dockerfile does exactly this on `dart:stable`. If the project has its own Dockerfile, `dart_frog build` copies that one instead (observed in the spike).

Executable sizes (amd64, measured from the built images): shelf 7.36 MB, dart_frog 7.40 MB. Image sizes as reported by `docker image inspect`: 4.96 MB and 4.97 MB.

Multi-arch: the official `dart:3.13.5` manifest includes linux/amd64 and linux/arm64 (checked with `docker manifest inspect`, 2026-10-12), so either option builds for the Oracle A1 VM with buildx. The arm64 build was not run in this spike; T-009 covers it.

#### 7. CLI or code generation requirements

- shelf: none. Routes are code. No build step beyond `dart compile exe`.
- dart_frog: the CLI is required for development (`dart_frog dev`, hot reload) and for production (`dart_frog build` generates the server entry point). That adds a 42-package build tool to CI and the Docker build, and a generation step to keep in sync. Route files use names like `routes/v1/games/[bggId].dart`, which the `file_names` lint in `package:lints/recommended.yaml` flags (seen in the spike: 1 analyzer issue until `// ignore_for_file: file_names` is added). T-006 asks for a shared strict lint set with zero issues, so every dynamic route needs that ignore, or the rule is disabled for `routes/`.

Note for the API contract: neither framework affects packages/api_contract. Both can share the same plain Dart DTOs with the app.

#### 8. Idle memory, measured in a linux/amd64 container

Setup: Docker Desktop 29.6.1 on Windows 11 (WSL 2 engine, amd64). Build image `dart:3.13.5` (digest of `dart:stable` at the time, same SDK: sha256:8604cbd137b6d67c24f49b916f2aa9b67d71b539576e0178bf161d831c9e344f). Both servers AOT compiled, `FROM scratch` runtime image, run with `--platform linux/amd64`. Script: `server/spike/measure.sh`. Each container started alone, received 6 GET /health requests, then sat idle for 20 s before sampling. RSS read from `/proc/1/status` through a busybox sidecar sharing the container's PID namespace (the scratch image has no shell).

| Server | Run | VmRSS (idle) | VmHWM (peak RSS) | cgroup usage (`docker stats`) |
|---|---|---|---|---|
| shelf + shelf_router | 1 | 8.2 MB (8384 kB) | 8.2 MB | 3.5 MiB |
| shelf + shelf_router | 2 | 8.2 MB (8424 kB) | 8.2 MB | 4.3 MiB |
| dart_frog | 1 | 8.2 MB (8424 kB) | 8.2 MB | 4.5 MiB |
| dart_frog | 2 | 8.4 MB (8556 kB) | 8.4 MB | 4.8 MiB |

Reading: about 8 MB RSS for both, a difference of 0.1 to 0.2 MB. Memory does not decide between them. Both are far below the PRD target of 512 MB idle for the whole Compose stack (PRD section 8.3, an [ASSUMPTION] target); PostgreSQL and Caddy will dominate. The cgroup number is lower than RSS because the executable's file pages are page cache that is not charged to the container. Not measured: memory under load, JIT mode, arm64. T-008 or T-010 should measure the real server with PostgreSQL connections under load.

#### 9. Recommendation

Use **shelf + shelf_router**, AOT compiled, on `FROM scratch`.

Why:
1. Same memory, same AOT path, same image size: no runtime advantage for dart_frog.
2. Smaller supply chain: 14 runtime packages, all from the Dart team or google.dev, and no build-time tool, against 23 runtime packages (including hot-reload packages in production dependencies) plus a 42-package CLI.
3. Tests cover the real pipeline (routing, middleware order, path parameters) by calling one `Handler` with real `Request` objects, which suits the brief's "every endpoint, every upstream failure" test matrix and the 80% coverage target. dart_frog's recommended tests skip routing and middleware composition.
4. No code generation and no lint exceptions, which fits T-006's zero-issue strict lints.
5. Ownership: shelf is the Dart team's and still receives fixes in 2026; dart_frog's 2026 activity is mostly upkeep after a move away from Very Good Ventures, with no statement about who maintains it. Since dart_frog sits on shelf anyway, choosing it adds a second risk without removing the first.

Costs we accept: no file-based routing (we keep one router file per feature, mounted under `/v1`), no hot reload (a server restart takes about a second), and our own small helpers for JSON responses and typed errors (we need typed errors anyway).

What would make us switch later:
- shelf or shelf_router marked discontinued on pub.dev, the dart-lang/shelf repository archived, or a security fix that stays unreleased. First candidate then: relic (serverpod.dev, BSD-3-Clause, 1.2.0 published 2026-03-11, described on pub.dev as "inspired by Shelf" with a simple migration from shelf, 2.0.0-rc.2 committed 2026-09-30). It is not recommended now because its 2.x API is still at release candidate and it has far fewer users (118 likes, 241,511 downloads in 30 days).
- dart_frog only if it shows steady runtime releases again with a named maintainer and we find we need something it gives and shelf does not. Nothing in the current requirements does.
- Any license change in the tree to something other than MIT, BSD, or Apache 2.0 (the dependency license check in CI, T-017, would catch it).
