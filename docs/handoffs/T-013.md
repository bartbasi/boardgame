#### Status mapping and retry rules

| Status or error | Failure | GET retried |
|---|---|---|
| 2xx with a JSON object that decodes | Ok | n/a |
| 2xx with invalid JSON, a non-object, or a decode error | Unexpected | no |
| 400, 422 | InvalidInput (code from the error envelope, else `unknown`) | no |
| 401, 403 | AccessDenied | no |
| 404, 410 | NotFound | no |
| 408 | Timeout | yes |
| 429 | RateLimited (with Retry-After if readable) | yes, unless Retry-After is over 30 s |
| 502, 503, 504 | ServiceUnavailable | yes, unless Retry-After is over 30 s |
| 500, 501, other 5xx, 3xx, other 4xx | Unexpected | no |
| connection error, `SocketException` | NoConnection | yes |
| connect, send, or receive timeout; 20 s budget used up | Timeout | yes (budget permitting) |
| cancel | Cancelled | no |
| bad certificate, transform timeout, anything else | Unexpected | no |

A retry waits for Retry-After when the response has one (at most 30 s), otherwise for the jittered backoff. If the wait would end at or after the 20 s deadline, the call returns the last failure at once instead of waiting.

### Proposed decisions

1. Failure hierarchy: the seven AC1 cases plus `AccessDeniedFailure` (401, 403), `CancelledFailure` (caller cancelled), and `ConfigurationFailure` (bad API_BASE_URL). Domain code gets the API error code through the domain enum `InvalidInputCode` instead of importing api_contract.
2. The status mapping and retry table above, including: retry GET on connection errors and timeouts as well as 429, 502, 503, 504; Retry-After honored on 503 as well as 429; when the next wait would pass the 20 s deadline, return the last failure at once.
3. Profile builds require https like release builds (`allowInsecureHttp: kDebugMode`).
4. `lib/core/domain/` is checked by the domain purity test, and domain code may not import `lib/core/data/`.
5. App tests read api_contract's JSON fixtures directly from `../packages/api_contract/test/fixtures/` instead of copying them, so they cannot drift.

#### What I checked and found sound

- Idempotency: only GET is retried (`retries = method == 'GET' ? policy.maxRetries : 0`, api_client.dart:109). POST gets one attempt for 503, 429, connection errors, and timeouts (tests AC9 and QA).
- Backoff: full jitter in [0, min(8 s, 500 ms x 2^(n-1))), seeded Random injected; AC4 bounds tested at both ends of the range and over 40 seeds.
- Retry-After: delta seconds and HTTP date, past dates give zero, over 30 s means no retry and the failure carries the wait (AC6, AC7). Honored on 502, 503, 504 as well as 429. A 30 s Retry-After (T-028 AC3) returns `RateLimitedFailure(retryAfter: 30 s)` at once because it would pass the 20 s deadline, which is what T-028 expects.
- 20 s deadline: a per-attempt `Timer(remaining)` completes the attempt with `TimeoutFailure` and cancels the dio request through a private `CancelToken`, so a hung socket cannot outlive the call. No wait is started if it would end at or after the deadline. Verified the hung-request test ends at exactly 20 s and the adapter saw the cancel.
- Cancellation: caller token checked before the attempt, during the attempt, and during the wait; returns `CancelledFailure`, never retried.
- Nothing throws across layers: `_send` has an `on Object` guard, `_decode` catches decoder errors, dio rejections go through `.then(onError:)`, and the dio interceptor chain converts interceptor exceptions to rejections (checked dio-5.11.1 dio_mixin.dart). `Failure.toString` carries no exception text.
- Host lock: paths must start with a single `/`; dio builds `baseUrl + path` (options.dart:662), so a leading `/` can never change the authority. `followRedirects = false`, so a 3xx cannot move the request to another host or to http.
- https: `allowInsecureHttp: kDebugMode` covers release and profile. Config rejects query, fragment, user info, and non-http(s) schemes.
- Logging: added only when `enableLogging` (kDebugMode); logs method, `uri.path`, status or `DioExceptionType.name`, and ms. No data, headers, query, or error message. No other logging in lib/.
- Domain purity: lib/core/domain imports only its own files; the purity checker now covers core/domain and forbids core/data.
- AC16: body must be a JSON object before `decode`; error statuses map by status alone, and `_inputCode` catches envelope decode errors.
- Dependencies: dio 5.11.1 MIT, dio_web_adapter 2.2.2 MIT (checked LICENSE files in the pub cache), clock Apache 2.0, fake_async Apache 2.0 (dev), mime already in the lockfile. No paid service.
- AndroidManifest main declares INTERNET (closes T-012 R1-G5 forward item).

#### Should fix

- R1-S1 app/lib/core/data/network/retry_policy.dart:52-58, app/test/qa/network_edge_cases_test.dart:173-181. `baseDelay.inMicroseconds * pow(factor, retry - 1).toInt()` overflows 64-bit int for large retry numbers: retry 46 gives a negative ceiling (so a negative Duration), and retry 60 and above gives 0 (no wait at all). Unreachable with the default 3 retries, but `RetryPolicy` is a public, configurable class, and the QA test "backoff stays sane for absurd retry numbers" passes only because 63, 64, 65, 100, and 1000 happen to wrap to 0, and it accepts 0 as "sane". Why it matters: a later policy change (or a different factor) silently removes backoff, and the test that claims to guard this would not notice. Fix: saturate before multiplying, for example loop doubling the ceiling and stop once it reaches `maxBackoff`, or compute in double and clamp (`min(maxBackoff.inMicroseconds.toDouble(), base * pow(factor, n - 1).toDouble())`). Strengthen the test: with `FixedRandom(0.5)` every retry from 6 up (including 46, 63, 1000) must give exactly 4 s.
- R1-S2 app/test/core/data/network/api_client_test.dart:494-501 ("slow 503s stop retrying before the limit"). Assertions are loose (`isErr`, `<= 20 s`, `< 4` requests) and would also pass if the client stopped after one attempt or returned the wrong failure. With 6 s per 503 and the seeded Random(42), the exact outcome is determined: assert the failure type (`ServiceUnavailableFailure`), the exact number of requests, and that elapsed is below 20 s by the expected amount. Same pattern in "connect timeouts plus retries stop at 20 s" (no request count).

#### Suggestions

- R1-G1 api_client.dart:108 and 171. The deadline and `remaining` use wall-clock `clock.now()`. A device clock change mid-call (NTP sync, user change) shifts the deadline; per-attempt timers are monotonic, so this is bounded but can exceed 20 s if the clock jumps back. Option: start one `Timer(policy.totalTimeout)` at call start that flips a "deadline reached" completer, and have attempts and waits race it. Timers are monotonic and fake_async drives them, so the tests keep working.
- R1-G2 api_client.dart:190-195 and 230-235. Each attempt and each wait registers a `whenCancel.then` closure on the caller's token that is never removed. Harmless for per-query tokens, but a long-lived token reused across many calls keeps every closure (and its Completer) alive until it is cancelled or collected. Note in the doc comment that callers should use one token per logical call, or detach listeners via a local flag.
- R1-G3 failure.dart:67. The server sends Retry-After on 503 `upstream_unavailable` (backlog T-022 AC7, T-023 AC7, T-025 AC8). `ServiceUnavailableFailure` drops it. copy.md `common.errorUnavailableBody` has no seconds today, so this is fine; if UX later wants "Try again in N seconds" for 503, add an optional `retryAfter` like `RateLimitedFailure`.
- R1-G4 api_client.dart:44. No cap on response size; a misbehaving proxy could send a very large body that is read fully into a String (QA showed 5 MB works). Consider rejecting bodies above a limit (for example via Content-Length check in the adapter path, or a stream with a byte cap) when the first large endpoint lands.
- R1-G5 test/architecture/domain_purity.dart:185. Domain may import any own-package file except feature data or presentation and core/data. lib/app/ and a future lib/core/presentation/ are not blocked by the path rule (only indirectly through the package:flutter ban). Consider listing allowed own-package roots (features/*/domain, core/domain) instead of listing forbidden ones.
- R1-G6 api_client.dart:15. Name clash risk: `JsonDecoder` is also a class in dart:convert. Any data file that imports both dart:convert and api_client.dart gets an ambiguous name. Consider `JsonObjectDecoder`.

- R1-S1 (fixed): `RetryPolicy.backoff` now grows the ceiling step by step and stops at `maxBackoff`, so no retry number can overflow (and a factor of 1 or less cannot loop). I tightened QA's test "backoff stays sane for absurd retry numbers" in app/test/qa/network_edge_cases_test.dart, as the orchestrator asked: with `FixedRandom(0.5)` it now asserts exactly 4 s for retries 6, 7, 10, 45, 46, 47, 62, 63, 64, 65, 100, 1000, and 2^30. The old version accepted 0, which is what the overflow produced. A comment in the test records the change.
- R1-S2 (fixed): the AC10 tests now assert exact outcomes, using `FixedRandom`:
  - "connect timeouts plus retries stop at 20 s": `TimeoutFailure`, exactly 2 requests, elapsed exactly 20 s, a 10.25 s gap, and the second request cancelled.
  - "slow 503s stop retrying when the next wait would pass 20 s" (replaces the loose test; random 0.9): `ServiceUnavailableFailure`, exactly 3 requests, elapsed exactly 19.35 s.
  - New: "slow 503s with a short last wait time out at exactly 20 s" (random 0.5): `TimeoutFailure`, 4 requests, elapsed exactly 20 s, and the last request cancelled.
- R1-G1 (done): each call now has one `_CallScope`. It holds a monotonic `Stopwatch`, used for `remaining`, and a single `Timer(totalTimeout)` for the deadline. Attempts and backoff waits race that deadline. Wall-clock time (`clock.now()`) is now used only to read Retry-After HTTP dates. `ApiClient` takes an optional `newStopwatch` factory: it defaults to `Stopwatch.new`, and tests pass `clock.stopwatch` so fake time drives it. New tests:
  - "the deadline ignores the wall clock (review R1-G1)" freezes the wall clock with `withClock(Clock.fixed(...))` and still gets 3 attempts and 19.35 s. A wall-clock deadline would have allowed a fourth attempt.
  - "the default stopwatch is a real monotonic Stopwatch" runs a 50 ms budget in real time.
- R1-G2 (done): each call registers one listener on the caller's `CancelToken`, through a small link object. Dart futures cannot remove listeners, so `close()` cuts the link at the end of the call; a long-lived token then keeps only an empty link, not the call. Attempts and waits use `scope.onEnd`, which is cleared after each one, so they no longer add listeners to the token. The class doc now asks for one token per logical call. New test: "one token reused across calls only affects calls that run when it is cancelled (review R1-G2)".
- R1-G5 (done): own-package imports in the domain purity check are now an allowlist. Domain code may import only `features/<feature>/domain/...` and `core/domain/...` (`isDomainPath`). The specific messages for feature data or presentation and for core/data stay; anything else gets "domain may only import domain files". Fixture changes:
  - The `clean` fixture's shared result moved to `core/domain/`.
  - The `transitive` fixture's flutter-importing file moved to `core/domain/colors.dart`. The test now picks the violation reached from the feature file, because that file is also checked on its own.
  - The new `outside_domain` fixture shows that pure Dart files in lib/app/ and lib/core/ui/ are refused.
  - New test: "isDomainPath allows only feature domain and core domain".
- R1-G6 (done): `JsonDecoder` is renamed to `JsonObjectDecoder`.
- R1-G3 (deferred, as the orchestrator directed): `ServiceUnavailableFailure` still drops Retry-After. Add an optional `retryAfter` when UX wants "Try again in N seconds" for 503.
- R1-G4 (deferred, as the orchestrator directed): no cap on response size yet. Add one when the first large endpoint lands.
