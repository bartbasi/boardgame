## Round 1

### Developer notes (backend-developer)

**What changed**

- `server/lib/src/http/rate_limiter.dart`: `RateLimiter`, an in-memory fixed-window counter. A client's window starts with its first request and lasts one minute; up to `limit` requests are allowed, later ones get the time left. Refused requests do not extend the window. Entries live in a `Map<int, int>` (key to packed window end and count) plus a `ListQueue<int>` in window order, so there are no per-entry objects; because every window has the same length and the clock is monotonic, insertion order is expiry order, and expiry and eviction always pop from the front (O(1) amortized per request). Expired entries are removed on every `hit`. When `maxTracked` keys are held, a new key evicts the oldest; `onFull` fires at most once a minute. The clock is injectable (`Duration Function() now`, default a `Stopwatch`).
- `server/lib/src/http/rate_limit.dart`: `ClientAddressResolver` (client IP rule below), `addressKey` (IPv4 to its 32-bit value, IPv4-mapped IPv6 to the same, other IPv6 to its /64 prefix), `rateLimit` middleware, `rateLimitedResponse` (429, `rate_limited` envelope, `Retry-After` whole seconds rounded up, at least 1), and `logRateLimiterFull` (warning `rate limiter full, evicting oldest entries` with `maxTracked` only).
- `server/lib/src/config/config.dart`: three optional variables, validated at startup with the existing all-problems-in-one-line rule (exit 78, never a value): `RATE_LIMIT_PER_MINUTE` (default 60 [ASSUMPTION], 1 to 10,000 [ASSUMPTION]), `RATE_LIMIT_MAX_TRACKED_IPS` (default 100,000 [ASSUMPTION], 1 to 200,000 [ASSUMPTION]), `TRUSTED_PROXY_ADDRESSES` (comma-separated IP literals, at most 10, default none). Added to `server/.env.example`.
- `server/lib/src/server_runner.dart`: builds the limiter from config and mounts `rateLimit` as the first (and for now only) `v1Middleware`, so T-066 attestation goes after it. /health and paths outside /v1 are not under it.
- `server/lib/src/logging/error_description.dart` (AC8): `ArgumentError`, `RangeError`, and `IndexError` are described as type, `name`, and `message` only, never `invalidValue`. Absolute URLs in any description now keep only scheme and host: user info, path, query, and fragment each become `<redacted>`; the existing query-string redaction outside URLs stays. The FormatException, HttpException, SocketException, ServerException, and PgException (T-019) cases are unchanged.
- `deploy/docker-compose.yml`: the `web` network gets a fixed subnet `10.213.7.0/24`, Caddy gets `ipv4_address: 10.213.7.10`, and the server gets `TRUSTED_PROXY_ADDRESSES: "10.213.7.10"`. `docker compose -f deploy/docker-compose.yml --env-file deploy/.env.example config -q` passes locally. No new deploy/.env variables.
- Docs: server/README.md (new "Rate limiting" section, describeError rules), deploy/README.md (Caddy section: how Caddy's address is configured and tested).

**Client IP rule (AC4, the T-005 design note)**

The direct peer is the socket address shelf_io puts in the request context (`shelf.io.connection_info`). Only if the peer equals (exact address, not prefix) one of `TRUSTED_PROXY_ADDRESSES` is the client the **last** X-Forwarded-For entry, which is the one Caddy appends. Everything to its left can be sent by the client and is never used. From any other peer the header is ignored. A trusted peer with no header, or a last entry that is not an IP literal (for example `ip:port` or `unknown`), is limited by its own address, which fails safe (limits more, never less). Caddy's docs say it ignores incoming X-Forwarded-* from untrusted clients by default (https://caddyserver.com/docs/caddyfile/directives/reverse_proxy, checked 2026-10-14); taking the last entry is correct either way.

How the address is configured: fixed subnet and `ipv4_address` in Compose, passed to the server as `TRUSTED_PROXY_ADDRESSES`. How it is tested: `server/test/config/compose_trusted_proxy_test.dart` reads docker-compose.yml and checks the trusted address equals Caddy's `ipv4_address`, lies in the `web` subnet, belongs to the caddy service, and parses with `Config.load`. The behavior is tested in-process and over real sockets through `bindAndServe` (below).

## Open questions

1. **IPv6 clients are limited per /64 prefix, not per full address [ASSUMPTION].** The ticket says "per IP". One subscriber normally gets a whole /64 and can use any of its 2^64 addresses, so a per-address limit is trivially bypassed and lets one client fill the table and evict everyone else's counts. /64 is the usual practice. If the PM wants per full address, `addressKey` is the only change (IPv6 keys would then need a hash, about twice the memory). IPv4 is per full address.
2. **Fixed window, not sliding.** A client can send 60 requests at the end of one window and 60 at the start of the next (120 in a few seconds). AC1 holds (at most 60 in any one window, and in the 10 s test). A sliding log would cost up to 60 timestamps per client (100,000 clients would not fit 64 MB). A two-window estimate is possible later if this matters.
3. **Upper bounds on the settings [ASSUMPTION]**: RATE_LIMIT_PER_MINUTE at most 10,000 and RATE_LIMIT_MAX_TRACKED_IPS at most 200,000 (memory, above). Neither is in the ticket.
4. **Eviction resets a client.** During a flood of more than 100,000 distinct addresses in a minute, a limited client can be evicted and start fresh. The ticket asks for oldest-first eviction, so this is by design; noted for the review.
5. **IPv6 and real client addresses on the VM (for T-071).** The limiter is only as good as the address Caddy sees. With Docker's default iptables publishing, IPv4 clients arrive with their own address. If the VM serves IPv6 and Docker's IPv6 is not enabled, IPv6 clients may arrive through docker-proxy as one gateway address and share a single limit. T-071 should decide IPv6 (or not publish AAAA).
6. **Subnet 10.213.7.0/24 [ASSUMPTION]** is outside Docker's default pools and Oracle's default VCN 10.0.0.0/16, checked against defaults only, not against the real VM. If `compose up` reports an overlap, change the three places together (the test checks they agree).

## Proposed decisions

1. Client IP: X-Forwarded-For is trusted only from the exact addresses in `TRUSTED_PROXY_ADDRESSES` (Caddy's fixed Compose address 10.213.7.10), and only its last entry is used; from any other peer the socket address is used. Default: no trusted proxy.
2. Rate limit key: IPv4 full address; IPv6 /64 prefix (open question 1).
3. Limiter algorithm: per-client fixed one-minute window starting at the first request; refused requests do not extend it; oldest-first eviction at the cap; a capacity warning at most once a minute with no address.
4. describeError: ArgumentError family logs name and message only; every absolute URL is reduced to scheme and host (path, query, fragment, user info redacted). This supersedes the T-008 rule that kept URL paths.
5. Rate limiting is mounted only on /v1 (not on unknown non-/v1 paths, which are cheap 404s).
