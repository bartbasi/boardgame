## Research notes for PM

For the T-002 instance to record in docs/api-research.md. Found while checking the brief's mandated scanner package against the license rule.

1. **mobile_scanner license and engines.**
   - Fact: mobile_scanner is published under BSD-3-Clause. It uses CameraX and Google ML Kit on Android and AVFoundation and Apple Vision on iOS. On Android it uses the bundled ML Kit barcode model by default; an unbundled variant is downloaded through Google Play services if `dev.steenbakker.mobile_scanner.useUnbundled=true` is set in android/gradle.properties.
   - Source: https://pub.dev/packages/mobile_scanner
   - Date checked: 2026-10-11
   - Quote: "This package uses by default the bundled version of MLKit Barcode-scanning for Android." The License heading shows "BSD-3-Clause".
   - Confidence: confirmed (official package page). The page states no minimum Android SDK or iOS version for the package itself: UNVERIFIED against our API 24 and iOS 15 assumption.

2. **Google ML Kit terms.**
   - Fact: The ML Kit terms incorporate the Google APIs Terms of Service. They are not an open source license, so ML Kit falls outside the project's MIT, BSD, or Apache 2.0 rule and needs user approval (PRD Q4).
   - Source: https://developers.google.com/ml-kit/terms
   - Date checked: 2026-10-11
   - Quote: the terms "incorporate and are subject to the Google APIs Terms of Service"; "you may not reverse engineer or attempt to extract the source code or any related software."
   - Confidence: confirmed. Whether ML Kit is free of charge is not stated on that page: UNVERIFIED.

3. **ML Kit data sent to Google, and our disclosure duty.**
   - Fact: ML Kit processes input on the device and does not send images or results to Google. It does contact Google servers for updates, and it sends performance and usage metrics to Google. The developer must tell users about this.
   - Source: https://developers.google.com/ml-kit/terms
   - Date checked: 2026-10-11
   - Quote: "ML Kit does not send that data and the resultant outputs to Google servers"; the APIs "send metrics about the performance and utilization of the APIs in your app to Google"; "You are responsible for informing users of your app about Google's processing of ML Kit metrics data."
   - Confidence: confirmed.
   - Impact: privacy policy (T-078), Google Play Data Safety answers (T-079), and the third-party components list (T-017).

**Proposed golden trimming rule.** The specs list 213 golden files across 13 screens (game-detail 32, collection 24, scanner 19, search 19, lookup-result 18, listings 16, price-history 16, backup-and-export 15, collection-item-edit 15, add-to-collection 10, app-shell 10, manual-entry 10, settings 9). For each screen:

1. One golden per visually distinct state, in light compact. States with the same layout that differ only in text (for example error and not found) share one golden; widget tests check the text.
2. One dark golden for the main success state, plus dark for a state that uses color roles the success state does not (for example an error container or the stale chip).
3. One golden at the screen's widest distinct layout (expanded, or landscape if it differs). Medium only when its layout differs from both compact and expanded.
4. One `text200` golden for the densest state.
5. Loading skeleton: one golden, light compact only.
6. Cap: 8 goldens per screen per milestone in which the screen changes [ASSUMPTION]. For example, game-detail would have at most 8 for M2, 8 for M3, and 8 for M4, and in practice about 17. A spec that needs more states its reason.
7. Anything dropped from the golden list stays covered by widget tests (states, labels, no overflow at 2.0, accessibility guidelines in both themes), which every UI ticket already requires.

Estimate: about 100 to 120 goldens in total instead of 213. Tickets need no change, because they require "every golden the spec lists".
