## Round 1

### Developer notes (backend-developer)

**What changed**

Four new DTOs and one new enum in packages/api_contract/, all additive within /v1, built the T-007 way (freezed 4, json_serializable checked mode, generated files committed):

- `GameSummary`: one game in a list (search results, lookup candidates).
- `SearchResponse`: body of `GET /v1/games/search?q=`.
- `LookupResponse` and `LookupStatus`: body of `GET /v1/lookup/barcode/{code}`.
- `GameDetailResponse`: body of `GET /v1/games/{bggId}`.

Stricter decoding than plain json_serializable, through small converters in lib/src/converters.dart (not exported):

- `bggId`, player counts, and play times must be whole numbers of at least 1. Plain json_serializable would turn `1.5` into 1 and accept 0; these throw `CheckedFromJsonException` naming the field. A whole-valued double such as `13.0` is accepted. Error messages never echo the rejected value.
- `yearPublished` must be a whole number; negatives are allowed (years before the common era).
- `fetchedAt` must be an ISO 8601 string in UTC (`Z` or an explicit offset). A timestamp with no zone is rejected because its meaning would depend on the reader's time zone. Encoding always writes UTC with `Z` (`DateTime.toUtc().toIso8601String()`).
- `code` in the lookup must be exactly 13 ASCII digits.
- `LookupResponse.fromJson` checks that the number of games fits the status (matched: exactly 1; candidates: at least 1; none and unavailable: 0; unknown: any) and throws `CheckedFromJsonException` with key `games` otherwise. This catches a server bug in the server's own endpoint tests (T-022 AC8, T-023 AC9, T-025 AC11 decode every 200 with these DTOs).
- `designers` and `publishers` default to an empty list when missing or null; the server always sends `[]`.

The README now documents every shape, the HTTP status for each error code (`upstream_unavailable` is 503 with Retry-After, never 500, per T-013), the "missing values are null, never 0 or empty" rule, the BGG page URL, the fixture layout, and a new rule for consumers: switch over `ErrorCode` or `LookupStatus` with a wildcard (see Contract changes).

**Decision: no `bad_request` error code (T-008 open question 4).** I decided not to add it. Reasons:

1. It would serve only requests whose URL the server cannot parse (a bad Host or X-Forwarded-Host). Caddy sets a valid Host for every request it forwards, so the app can never receive it, and the app could not act on it differently from `not_found` anyway (the app would show a generic error either way).
2. Adding an `ErrorCode` value breaks the app's build today: app/lib/core/data/network/failure_mapper.dart has an exhaustive `switch` over `ErrorCode` with no wildcard, so a new value is a compile error in app.yml, even though the wire format stays compatible. I cannot change app/, and this ticket must be green in CI.
3. The current 404 already uses the typed envelope and leaks nothing.

Revisit if a client-visible case for a generic 400 appears. Before any new `ErrorCode` value is added, the flutter-developer should add a wildcard to that switch (see Contract changes). The README states that there is no `bad_request` code.

**Image fields (PRD Q5, docs/decisions.md 2026-10-12).** `GameSummary.thumbnailUrl` (nullable) exists only because AC2 requires it. The server sends null until BGG answers how its images may be used. The screens already handle a missing thumbnail, so filling it later needs no contract change. `GameDetailResponse` has no image field: AC4 lists "image" only as an example, and Q5 says no cover images for now. A nullable `imageUrl` can be added later without a contract break.

**BGG page URL (AC9).** Both `GameSummary` and `GameDetailResponse` carry a required `bggUrl`, built by the server. Its format is `https://boardgamegeek.com/boardgame/{bggId}`, without `www` (BGG-03). How the format was checked: I could not confirm it on BGG's own site. On 2026-10-13, `https://boardgamegeek.com/boardgame/13` returned HTTP 403 to both WebFetch and curl (the same block docs/api-research.md reports for boardgamegeek.com). The evidence I have is secondary: Wikidata's "BoardGameGeek ID" property (P2339) gives the formatter URL `https://boardgamegeek.com/boardgame/$1` (read on 2026-10-13 through https://www.wikidata.org/w/api.php?action=wbgetclaims&entity=P2339&property=P1630). A person should open one game page and one expansion page in a browser to confirm (see Open questions). Because the URL is a server-built string, the server can change the format without a contract change.

### Contract changes for flutter-developer

All additive. Nothing existing changed. New exports from `package:api_contract/api_contract.dart`:

**`GameSummary`** (used inside `SearchResponse.games` and `LookupResponse.games`)

| Field | Dart type | JSON | Notes |
|---|---|---|---|
| `bggId` | `int` | integer, required | At least 1. |
| `name` | `String` | string, required | |
| `yearPublished` | `int?` | integer or null | Never 0 from the server; may be negative. |
| `thumbnailUrl` | `String?` | string or null | Always null for now (PRD Q5). Keep the no-image layout. |
| `bggUrl` | `String` | string, required | The game's BGG page. Use it for the "Powered by BGG" link; never build BGG URLs in the app. |

**`SearchResponse`**: `query` (`String`, the server's normalized query, may differ from what the app sent) and `games` (`List<GameSummary>`, may be empty; server order, exact matches first).

**`LookupResponse`**: `code` (`String`, GTIN-13, 13 digits), `status` (`LookupStatus`), `games` (`List<GameSummary>`).

**`LookupStatus`** enum: `matched` (exactly 1 game), `candidates` (1 or more), `none` (0), `unavailable` (0; GameUPC down, still a 200, offer title search), `unknown` (client side only, any count). `wireName` gives the JSON value. A busy BGG queue is not a status: it is 503 `upstream_unavailable`.

**`GameDetailResponse`**

| Field | Dart type | JSON | Notes |
|---|---|---|---|
| `bggId` | `int` | integer, required | At least 1. |
| `name` | `String` | string, required | |
| `yearPublished` | `int?` | integer or null | |
| `minPlayers`, `maxPlayers` | `int?` | integer or null | At least 1 when present. Equal values mean a single count (`gameDetail.playersValueSingle`). |
| `minPlayTimeMinutes`, `maxPlayTimeMinutes` | `int?` | integer or null | Minutes, at least 1 when present. |
| `designers`, `publishers` | `List<String>` | array of strings | Never null in Dart; empty means none. Unmodifiable. |
| `description` | `String?` | string or null | Plain text with `\n` line breaks. |
| `bggUrl` | `String` | string, required | As above. |
| `fetchedAt` | `DateTime` (UTC) | ISO 8601 string, required | When the server fetched from BGG; use it for `gameDetail.updatedLabel` together with the device's own cache time. |

Decoding: every new `fromJson` throws `CheckedFromJsonException` (already re-exported) for a missing, null, or wrong-typed required field and for the value rules above; map it to the unexpected failure as T-013 does for error bodies (T-028 AC4).

## Open questions

1. **BGG field names are not in docs/api-research.md.** Section 1.4 says "Response field names (name, yearpublished, minplayers, and so on) were not captured", and the section 10.8 comparison rates BGG's year, players, play time, designers, publishers, and description as "Expected; fields not yet recorded". So, strictly, research confirms none of the game detail fields. I included the fields that AC4 names and game-detail.md needs for M2 (name, year, players, play time, designers, publishers, description), all nullable or empty-list, because the contract is our own shape and a missing BGG value becomes null without a contract change. T-021 must record real `thing` responses (after the BGG token, T-087) and the PM should add the field facts to api-research.md; if BGG lacks one of these, the server sends null and we can drop it in a /v2. If the PM reads AC5 strictly instead, these fields should be removed now; please decide.
2. **Spec fields left out:** the cover image on game detail (game-detail.md "Cover", AC4's "image") is left out because of PRD Q5, not for lack of research. Nothing else that the M2 specs show is missing. Later specs (rating, rank, weight, minimum age, expansions) are not in M2 and are not in research.
3. **BGG page URL format not confirmed on BGG's site** (403 from this environment). Please have a person open `https://boardgamegeek.com/boardgame/13` and an expansion id under `/boardgame/{id}` in a browser and confirm both load (or redirect) without `www`. If expansions need `/boardgameexpansion/{id}`, the server builds that from the item type; no contract change.
4. **EAN-8 normalization:** T-025 AC2 says UPC-A normalizes to GTIN-13 with a leading zero but does not say what an EAN-8 becomes. The contract requires 13 digits, so an EAN-8 such as `96385074` would have to be sent as `0000096385074` (left-padded). T-025 and T-026 (app) must use the same rule; please confirm it in the backlog.

## Proposed decisions

- 2026-10-13, T-018: no `bad_request` error code; unparseable request URLs keep 404 `not_found`. Any new `ErrorCode` or `LookupStatus` value first needs a wildcard in the app's switches. (Reasons above.)
- 2026-10-13, T-018: the contract validates values, not only types: positive whole numbers for ids, player counts, and play times; whole-number years; UTC timestamps; 13-digit lookup codes; and a games count that fits the lookup status. A violation is a `CheckedFromJsonException`.
- 2026-10-13, T-018: optional fields are always sent, with explicit null (lists as `[]`), never 0 or an empty string for missing values. `thumbnailUrl` stays null until PRD Q5 is answered; no image field on game detail.
- 2026-10-13, T-018: `bggUrl` (`https://boardgamegeek.com/boardgame/{bggId}`) is built by the server and carried in every game summary and detail response.
