## Round 1

### Developer notes (backend-developer)

**What changed**

Four new DTOs and one new enum in packages/api_contract/, all additive within /v1, built the T-007 way (freezed 4, json_serializable checked mode, generated files committed):

- `GameSummary`: one game in a list (search results, lookup candidates).
- `SearchResponse`: body of `GET /v1/games/search?q=`.
- `LookupResponse` and `LookupStatus`: body of `GET /v1/lookup/barcode/{code}`.
- `GameDetailResponse`: body of `GET /v1/games/{bggId}`.

Stricter decoding than plain json_serializable, through small converters in lib/src/converters.dart (not exported):

- `bggId`, player counts, and play times must be whole numbers of at least 1. Plain json_serializable would turn `1.5` into 1 and accept 0; these throw `CheckedFromJsonException` naming the field. A whole-valued double such as `13.0` is accepted. Error messages never echo the rejected value.
- `yearPublished` must be a whole number; negatives are allowed (years before the common era).
- `fetchedAt` must be an ISO 8601 string in UTC (`Z` or an explicit offset). A timestamp with no zone is rejected because its meaning would depend on the reader's time zone. Encoding always writes UTC with `Z` (`DateTime.toUtc().toIso8601String()`).
- `code` in the lookup must be exactly 13 ASCII digits.
- `LookupResponse.fromJson` checks that the number of games fits the status (matched: exactly 1; candidates: at least 1; none and unavailable: 0; unknown: any) and throws `CheckedFromJsonException` with key `games` otherwise. This catches a server bug in the server's own endpoint tests (T-022 AC8, T-023 AC9, T-025 AC11 decode every 200 with these DTOs).
- `designers` and `publishers` default to an empty list when missing or null; the server always sends `[]`.

The README now documents every shape, the HTTP status for each error code (`upstream_unavailable` is 503 with Retry-After, never 500, per T-013), the "missing values are null, never 0 or empty" rule, the BGG page URL, the fixture layout, and a new rule for consumers: switch over `ErrorCode` or `LookupStatus` with a wildcard (see Contract changes).

**Decision: no `bad_request` error code (T-008 open question 4).** I decided not to add it. Reasons:

1. It would serve only requests whose URL the server cannot parse (a bad Host or X-Forwarded-Host). Caddy sets a valid Host for every request it forwards, so the app can never receive it, and the app could not act on it differently from `not_found` anyway (the app would show a generic error either way).
2. Adding an `ErrorCode` value breaks the app's build today: app/lib/core/data/network/failure_mapper.dart has an exhaustive `switch` over `ErrorCode` with no wildcard, so a new value is a compile error in app.yml, even though the wire format stays compatible. I cannot change app/, and this ticket must be green in CI.
3. The current 404 already uses the typed envelope and leaks nothing.

Revisit if a client-visible case for a generic 400 appears. Before any new `ErrorCode` value is added, the flutter-developer should add a wildcard to that switch (see Contract changes). The README states that there is no `bad_request` code.

**Image fields (PRD Q5, docs/decisions.md 2026-10-12).** `GameSummary.thumbnailUrl` (nullable) exists only because AC2 requires it. The server sends null until BGG answers how its images may be used. The screens already handle a missing thumbnail, so filling it later needs no contract change. `GameDetailResponse` has no image field: AC4 lists "image" only as an example, and Q5 says no cover images for now. A nullable `imageUrl` can be added later without a contract break.

**BGG page URL (AC9).** Both `GameSummary` and `GameDetailResponse` carry a required `bggUrl`, built by the server. Its format is `https://boardgamegeek.com/boardgame/{bggId}`, without `www` (BGG-03). How the format was checked: I could not confirm it on BGG's own site. On 2026-10-13, `https://boardgamegeek.com/boardgame/13` returned HTTP 403 to both WebFetch and curl (the same block docs/api-research.md reports for boardgamegeek.com). The evidence I have is secondary: Wikidata's "BoardGameGeek ID" property (P2339) gives the formatter URL `https://boardgamegeek.com/boardgame/$1` (read on 2026-10-13 through https://www.wikidata.org/w/api.php?action=wbgetclaims&entity=P2339&property=P1630). A person should open one game page and one expansion page in a browser to confirm (see Open questions). Because the URL is a server-built string, the server can change the format without a contract change.

## Round 2

### Developer notes, round 2 (backend-developer)

**What changed** (main merged first, 503beae)

- T-018-B1 fixed: `_wholeNumber` in packages/api_contract/lib/src/converters.dart accepts a double only when its absolute value is at most 2^53 - 1, the largest whole number a double holds exactly. Beyond that `double.toInt()` can clamp (1e300 became the 64-bit maximum); such values now throw, and inside a DTO that surfaces as `CheckedFromJsonException` naming the field. JSON integers are unaffected.
- T-018-B2 fixed: `UtcDateTimeConverter` still parses with `DateTime.parse` and requires UTC, then reads the written `YYYY-MM-DDThh:mm[:ss]` fields, rebuilds them with `DateTime.utc`, and requires every field to come back unchanged. Month 13, day 45, 29 February in a non-leap year, 31 April, hour 24, minute 60, and second 60 are rejected instead of rolled over. It also now requires the extended form with dashes and colons: the compact `20261013T081530Z`, which `DateTime.parse` accepted, is rejected. The server sends the extended form (`toIso8601String`).
- README aligned with docs/decisions.md 2026-10-13: the round 1 sentence telling consumers to use a wildcard is replaced by the recorded rule (the app's exhaustive switches are intentional; whoever adds a value updates the app in the same change). The lookup `code` row now states the confirmed key rule (UPC-A gets one leading zero, EAN-8 five). This answers round 1 open question 4 and the `bad_request` proposal.

**Tests added**

- game_detail_response_test.dart: "impossible dates and times are rejected, not rolled over (B2)" (the seven cases above) and "real edge dates are accepted" (the 2028 leap day, end of year with microseconds, minutes without seconds, an offset that crosses midnight).
